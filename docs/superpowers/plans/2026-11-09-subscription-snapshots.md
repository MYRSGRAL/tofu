# Подписки: загрузка, staged-обновление и постоянный snapshot

Основание: `docs/specs/data-and-contracts.md`, разделы 1–4. Это продолжение
импортера, а не готовность GUI или всех форматов native JSON к запуску.

1. Переносимый controller связывает ticket загрузки с уникальным экземпляром,
   поколением источника, revision snapshot и номером запроса. Новая загрузка,
   отмена и смена источника инвалидируют старый результат. Отчёт импорта
   просматривается до commit; явное согласие потребляет именно этот candidate.
   Пустой/неразбираемый ответ не удаляет последний snapshot. Native JSON
   остаётся отдельным opaque-источником с обязательным review, без активации.
2. Linux FetchHost: HTTPS, ручные редиректы, общий deadline, отмена, ограниченное
   потоковое чтение, закрепление проверенного DNS-набора и проверка TCP peer.
   Публичный источник запрещает private/reserved IP на каждом переходе.
   Исключение локального источника задаётся явно. Validators привязаны к URL.
   Ошибки и Debug не раскрывают URL, заголовки и тело.
3. SOCKS не предоставляет фактический peer конечного сервера через reqwest.
   До аттестованной проверки внутри engine этот маршрут явно неподдержан;
   автоматического перехода на Direct нет. Это незакрытая часть контракта.
4. Постоянное хранение: один SQLite writer, transactional CAS по поколению
   источника/revision; чувствительные записи AEAD с ключом Secret Service,
   без plaintext fallback. Ошибки ключа/БД не сбрасывают существующие данные.
   Этот шаг следует после стабилизации staged-контракта и FetchHost.

Проверки: старый snapshot после ошибок/отмены; устаревшие/чужие tickets и
approvals; review частичного импорта; bounded redirects/body; DNS/IP SSRF;
условные запросы; отсутствие скрытого route fallback. Затем сбой транзакции,
неверный ключ и офлайн-восстановление. Перед PR — workspace fmt/clippy/tests,
MSRV/Android compile-check и независимый review конкретного diff.
