# FR16: ограниченная дисковая ротация событий

Кандидат реализации; не является подтверждением всего FR16.

`EventLog::with_disk(data_dir)` используется production backend при создании Actor.
Открытие, восстановление, запись, ротация и sync выполняются одним отдельным
потоком. Producer передаёт только принятые ring события через очередь 128;
`try_lock`/`try_send` отбрасывают запись при конкуренции/переполнении, без ожидания
диска. Потеря дискового события не удаляет событие из ring.

## Хранение и безопасность

Имена: `events.log`, `events.1.log`–`events.4.log` в `data_dir/logs`.
Каждый файл ограничен 4 MiB; перед превышением выполняется ротация.
Каталог data_dir и logs принадлежат текущему UID и имеют 0700; файлы — 0600,
regular, текущий UID, ровно одна hardlink. Ancestors открываются относительно
дескриптора, без symlink; допускаются root/current UID, без group/other write.
На logs удерживается exclusive nonblocking flock весь срок жизни consumer.
Неподходящие объекты не исправляются и не удаляются. Чужие имена не затрагиваются.
Другой процесс того же UID не является изолированным противником.

Запись v1 содержит девять ASCII полей: версия, event ID, source code,
event code, наличие value, i32 value, наличие context, session ID, generation.
Source: App=1, Engine=2; события StartRequested=1, ProcessSpawned=2,
StopRequested=3, CleanupConfirmed=4, CleanupFailed=5, ProcessExited=6.
Нет произвольных строк, Debug, native bytes, конфигурации или путей.
Максимальная запись — 192 байта. ID относятся к текущему процессу и после
restart могут повторяться; старые файлы в memory ring не импортируются.

На restart проверяются размеры, типы/права/владелец/ссылки всех пяти файлов,
затем завершённые записи. Partial tail до 192 байт обрезается до последнего LF
и синхронизируется. Невалидная полная запись или более длинный хвост — отказ.
Ротация последовательными rename не транзакционна: crash может потерять
часть истории. Exactly-once и сохранность при потере питания не гарантируются.

## Lifecycle

`DiskLogGuard` предоставляет stats, request_shutdown и bounded wait_closed.
После request_shutdown новые producer-вызовы отклоняются; consumer завершает
уже допущенные записи. Поток синхронизирует dirty файл раз в секунду,
включая непрерывный поток событий; без dirty данных использует blocking recv.
На shutdown выполняется заключительный sync. При I/O ошибке sink отключается
до следующего запуска, без retry-loop и без raw error text.

Stop/отзыв сессии не ждут sink. Final shutdown backend сохраняет guard и каждые
10 мс асинхронно проверяет Done с нулевым timeout. Пока writer не завершился,
`closed` и acknowledgement control.closed не выдаются. Длительность syscall
не ограничена; зависший диск оставляет host в pending drain. Blocking join
до is_finished отсутствует. Drop только сигналит и не доказывает drain.
Ошибка записи/sync отражается в IoFailed/io_errors; завершение потока после
ошибки подтверждает прекращение I/O, но не успешную сохранность данных.
Bridge JSON/commands/error_context не изменены.

Счётчики насыщаются: enqueued, written (записано, не обязательно durable),
dropped_full (включая конкуренцию producer), dropped_closed, io_errors,
recovered_partial. Статусы: Starting, Active, Closed, Refused, IoFailed,
ThreadFailed. После ошибки часть принятых записей может остаться незаписанной;
разность enqueued/written показывает это после завершения.

## Проверка кандидата

Rust 1.85.1: `cargo test -p yonik-linux --lib event_log --locked` — 14 passed,
один существующий тест закреплённого native core ignored (core не предоставлен).
`cargo test -p yonik-desktop --features test-support --test disk_log_host
--test logs_save_ack --locked` — оба теста passed. Production test получает
EventLog через существующий test-support handle, создаёт типизированные события,
проверяет реальный файл после final shutdown и повторно получает exclusive lock.
`cargo clippy -p yonik-linux -p yonik-desktop --features
 yonik-desktop/test-support --all-targets --locked -- -D warnings` и
`cargo fmt --all -- --check` — passed.

Stalled-consumer fixture удерживает thread/guard после false от wait_closed(100ms),
затем разрешает drain и проверяет все 128 записей. Write failure проверяется
readonly fd, fsync failure — test-only `/dev/null` после успешного write;
IoFailed и io_errors подтверждаются. Foreign UID проверяется подменённым stat
fixture, без реального chown/capabilities. Файловые link/mode/type/size controls
используют реальные объекты. Crash recovery проверяется незавершённым хвостом,
а не принудительным отключением питания/kill во время rename.
