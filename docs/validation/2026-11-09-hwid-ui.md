# HWID Remnawave и второй проход UI

Причина повторной переработки: пользователь подтвердил, что первый визуальный
pass недостаточно заметен. Проверка `/proc/<pid>/exe` и SHA256 доказала запуск
новой сборки; списывать замечание на старый процесс было бы неверно.

Главная теперь содержит карточку сервера сверху, кнопку питания 224 px,
статус и отдельную карточку избранного снизу. Настройки открываются списком
пяти разделов, затем отдельной лениво создаваемой панелью. Back/Escape сначала
возвращают к списку настроек, затем домой. В заголовке и About виден build ID.
Новых idle-таймеров, blur/shader эффектов, WebView и зависимостей не добавлено.

## HWID

Контракт проверен по [официальной документации](https://docs.rw/features/hwid-device-limit/)
и [Remnawave backend 01a4059](https://github.com/remnawave/backend/blob/01a4059f2da3e22e1b82be58751a408f3d3de750/src/modules/subscription/subscription.service.ts).

- Передаётся только `x-hwid`, по явному opt-in подписки; по умолчанию отсутствует.
- Формат провайдера: 10–64 ASCII-символа из букв, цифр, `=` и `-`.
  tofu создаёт 16 случайных байт → 32 hex-символа. Железо/machine-id не читаются.
- ID сохраняется в зашифрованном source payload до запроса, стабилен после
  перезапуска и выключения/повторного включения опции. В DTO остаётся только bool.
- Старый v1 payload без новых полей читается с выключенной опцией. Любой
  присутствующий сохранённый ID проверяется, даже когда опция выключена.
- Смена настройки отменяет прежнее согласие/refresh, меняет generation,
  инвалидирует validators и автоматически повторяет загрузку. Старый snapshot
  сохраняется при отказе провайдера.
- `x-hwid-not-supported` и `x-hwid-max-devices-reached` имеют приоритет перед
  общим `x-hwid-limit`: последний может означать и отсутствие HWID. Проверка
  выполняется до status/304/импорта, в том числе при HTTP 200 с fallback-телом.
- При межorigin-редиректе HWID-запрос останавливается до передачи ID второму
  origin. Для явно разрешённого локального HTTP-источника действуют те же правила.

## Проверки

- Linux layer: полный набор 207 тестов; HWID-набор после исправления review — 9.
- Desktop: 7 unit + 23 integration; opt-in/toggle/restart, wire capture,
  busy, stop/shutdown, отсутствие ID в DTO. Namespace gate отдельно ignored.
- Build script: MSRV, explicit build ID, Git-absent fallback, отклонение
  управляющих/Unicode/слишком длинных значений без их печати.
- GUI: 68 действий, включая navigation/back, избранное, About/build ID,
  HWID cancel/reset, выключение/включение с автоматическим refresh; четыре
  локальных HTTP-запроса доказывают последовательность ID/ID/без ID/тот же ID.
- Реальные HWID и машинные идентификаторы провайдеру в тестах не отправлялись.

Отдельно выполнены шесть реальных одиночных подключений через Xray с
параллельностью два: два HTTP 204, два timeout TLS, ещё два EOF/reset на этапе
TLS. Все прошли config-check, открыли собственный SOCKS listener и SOCKS CONNECT.
Прогон занял 23,3 с; ошибки TLS не доказывают неверные credentials. URL, тело
подписки и скомпилированные конфигурации оставались в RAM, HWID не отправлялся.
Все тестовые процессы и FD закрыты; aggregate evidence находится в
`local/validation/private-connectivity/summary.json` (`probe_valid=true`).

Это не подтверждает системный TUN, полную матрицу Linux DE и длительные замеры
Wayland/idle/hidden. Работоспособность proxy-сервера не следует из успешной
загрузки подписки или config-check ядра.
