# G-APP: нативный baseline executable-условий Linux TUN

База: `db8226ef585b8251fe02ca3dbbe0f7ac759fc636`. Android отложен.
Полный P15/FR20/G-APP **не пройден**.

Существующий `compile_system_policy` теперь компилирует `Conditions.executables`
для IP-only TUN. SOCKS compiler сохраняет отказ ProcessAttribution. Domain/DNS,
helper и глобальные capabilities не изменены. Внутренний source adapter добавляет
`process` (Xray) либо `process_path` (sing-box) в то же правило назначения,
ограничивая его inbound `system-tun`. OR путей и AND назначения сохранены.
Пути ограничены 32 значениями на правило, 4096 байт на путь, суммарно 1 MiB;
относительные, управляющие символы, trailing slash, пустые/точечные компоненты
отклонены. Остальные проверки compiler продолжают действовать. Ошибка не
публикует частичный artifact; публичного JSON mutator нет.

## Фактические маршруты

`tests/isolatedfixture/attribution_gate.py` запускается в новом user/net/pid/mount
namespace с отдельным `/proc`. В нём только lo и собственный TUN. Две копии Python
с одинаковым basename `client` и различными точными путями одновременно открывают
сокеты после общей временной отметки. Это дочерние сетевые процессы; атрибуция
проверяет их executable, а не executable родителя. PID в policy отсутствует.

Для каждого ядра: TCP/UDP × IPv4/IPv6 × два назначения × два процесса = 16.
Первый путь + назначение `.2`/`::2` → настоящий VLESS peer → marker P;
первый путь + `.4`/`::4` → BLOCK; второй путь → DIRECT marker D на обоих
назначениях. Отсутствующий дополнительный executable проверяет OR списка.
Маршрут каждого назначения проверяется через `ip -j route get` до соединения.
Второе основное ядро не используется; peer того же типа — синтетический сервер.

Ещё 16 на каждом ядре: ядро помещено во вложенный PID/mount namespace и не
видит PID клиентов при общем netns. Все потоки получают default DIRECT. Xray
логирует `no process found for inode`; sing-box — ошибку поиска владельца.
Это unknown owner потока, **не** доказательство отказа активации при утрате прав.

Все четыре серии прошли 16/16. Сгенерированные evidence вне Git/TTL:
`/home/myrs/projects/yonik/local/validation/g-app-db8226/`.
Там исходный `*-compiled.json`, policy, исполняемый `*-config.json`, результаты,
логи и `hashes.json`. Для запуска сохраняются compiler rules/source selectors;
диагностические изменения: замена inbound на минимальный нативный TUN с тем же
тегом, удаление SOCKS/probe listeners, DIRECT redirect/override к marker,
debug logging. Это проверка source routing, **не** lifecycle production helper
или external TUN adapter. JSON содержит только синтетические credentials.

## Источники и ресурсные границы

Проверены закреплённые primary sources:
[Xray matcher](https://github.com/XTLS/Xray-core/blob/v26.10.31/app/router/condition.go),
[Linux FindProcess](https://github.com/XTLS/Xray-core/blob/v26.10.31/common/net/find_process_linux.go),
[sing-box searcher](https://github.com/SagerNet/sing-box/blob/v1.14.4/common/process/searcher_linux.go),
[process cache](https://github.com/SagerNet/sing-box/blob/v1.14.4/route/process_cache.go).
Их точные копии и hashes находятся в evidence. Xray действительно поддерживает
Linux process lookup; оснований объявлять его unsupported нет. Но FindProcess
линейно просматривает socket tables, затем `/proc/*/fd` при каждом matcher;
ограниченный кэш в этом пути не обнаружен. Sing-box использует socket_diag и
кэш путей с временем жизни 1 s, ёмкостью 64 UID; размер содержимого UID зависит
от числа процессов. Rust scans/tasks не добавлены.

Измерены end-to-end задержки успешных новых потоков (12 на серию):
Xray median 1349.5 µs/max 2111 µs, unknown 855/2221 µs;
sing-box 2196.5/3236 µs, unknown 2274/3909 µs. Они включают lookup, routing,
соединение и marker exchange; **не являются отдельной стоимостью owner lookup**.
Для оставшегося ресурсного требования нужен native profiler/инструментирование
lookup либо согласованный bounded owner API в ядре. Go/core patches не делались.

## Матрица остатка

- A-01: доказан минимальный native baseline двух executable и трёх действий.
- A-02: доказан фактический дочерний Python owner; браузер/AppImage/Flatpak/Wine не проверены.
- A-03: TCP/UDP IPv4/IPv6 доказаны; системный DNS и локальный proxy attribution не проверены.
- A-04: AND executable+CIDR и OR executable доказаны; домены, port, ru-direct/VPN не проверены.
- A-05: unknown owner → default доказан; полная потеря механизма до Apply не проверена.
- A-06: одинаковый basename разных путей доказан; PID reuse/PreparedPlan не проверены.
- A-07: UI/generation/lifecycle вне scope.
- A-08: строгая валидация путей проверена Rust тестом; каталог/скрытый экран не проверялись повторно.

Нужное продолжение root: production capability/privilege preflight и активация
политики, resource budget/cache и точное измерение owner cost, оставшаяся матрица.
Ни compile-check, ни этот baseline не закрывают весь gate.

Проверки реализации: Rust 1.85.1: 33 engine tests прошли; all-targets check через
закреплённый `clippy-driver` с `CLIPPY_ARGS=-D__CLIPPY_HACKERY__warnings` прошёл.
`cargo fmt --all -- --check` и Ruff check/format прошли. Обычный Clippy в окружении
AppImage выбирал 1.97 и обнаружил существующий collapsible_match в lib.rs:166;
этот посторонний код не исправлялся. Cargo.lock после автоматической перестановки
секций восстановлен побайтно из базы; зависимости не изменены.

Минимальное предложение root для ограниченного native lookup: сохранить текущий
FindProcess/owner контракт, добавить deadline и бюджеты socket-table rows,
proc entries и FD entries; при исчерпании возвращать отдельный unknown reason,
кэш ограничить ёмкостью/TTL и привязкой к netns, tuple и проверенной идентичности
процесса. Для Xray это требует изменения существующего Go lookup, не нового
Rust catalog. Такая реализация здесь не разрешена и не начиналась. Это ресурсный
остаток; функционального запрета Linux process selector не обнаружено.
