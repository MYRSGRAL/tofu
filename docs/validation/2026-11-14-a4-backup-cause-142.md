## Причина и различающий эксперимент

`tools/a4_userdata_worker.py::inspect` использовал
`with sqlite3.connect(...mode=ro) as db`. Контекстный менеджер Connection
завершает транзакцию, но **не закрывает соединение**. SQLite statement cache
образует циклические ссылки; окончательное закрытие зависит от GC.
Readonly inspect поэтому может удерживать live DB/WAL/SHM и SQLite read locks.
Maintenance требует `BEGIN EXCLUSIVE` на source после закрытия production
handles (`crates/yonik-linux/src/repository/backup.rs:377`). Чужой для product,
но собственный fixture reader мешает этому gate. Ошибка Repository::Conflict
типизированно переводится в `maintenance_copy_conflict`, UI message `busy`.
Это дефект нашего harness, не доказанный дефект SubscriptionService/actor.

Новый run2 воспроизводит проблему на прежнем immutable бинарнике:

1. Штатный Copy diagnostics UI → private X11 clipboard → строгий существующий
   D2 validator: request1, generation0, `maintenance_copy_conflict`,
   stage `maintenance_copy`. Admission/revision проверка этого запроса пройдена.
2. Actual Cancel text review завершился: модалка исчезла, страница Servers
   доступна (`11-cancel-complete.png`). После правильно выбранного нового
   private destination Backup прошёл (`14-aftercancel-busy.png`: вопреки имени
   screenshot показывает **сохранённую копию**), D2 errors=[], schema3/integrity OK.
3. Вызван inspect. `worker-fds-after-inspect.json` фиксирует Python PID1825917,
   live FD6/7/12 и POSIX READ locks source и SHM. Product PID отдельный.
4. В новый `storage/copies/backup4.sqlite` выбран basename через normal GUI.
   `16-reader-red-path.png` и `17-reader-red-result.png`; D2 request4,
   `maintenance_copy_conflict`. Копия не создана. Подмена API/ключа/backup нет.

В run3 **единственное семантическое изменение worker** — explicit
`contextlib.closing(sqlite3.connect(...))` в inspect. Снова вызван тот же
inspect; `fd-after-inspect.json`: у Python PID1843781 нет SQLite FD. Затем
normal GUI Backup в private `copies/backup3.sqlite` прошёл, D2 errors=[],
копия schema3/integrity OK. Candidate/service/доступ к ключу те же.
Отдельный regression test воспроизводит SQLite EXCLUSIVE RED при незакрытом
readonly connection и GREEN после closing; writer закрыт до обеих проверок.

Это прямой RED→GREEN для причины в harness. У run70c нет сохранённого D2/FD
снимка в момент отказа: историческим попыткам не присваиваются задним числом
новые typed metadata. Их неизменённый report остаётся фактом прежнего refusal.
Новый эксперимент устраняет blocker без изменения product.

## Cancel, admission и диагностические пределы

Actor.service — SubscriptionService. Никакой связи с privileged helper здесь
не доказано и для этого gate не требуется. Empty system bus из прошлого run
не использован как DB/admission различитель.

На отказах run2 request1/4 typed ACK имеет stage **copy**, поэтому broad
admission flags, maintenance_available и revision не отвергли эти запросы;
controller дошёл до копирования. После Cancel тот же backend успешно завершил
Backup. Это существенно сильнее гипотезы по одной UI-строке busy.
Точные raw ready/maintenance_available/revision/currentoperation не экспортируются
закрытым D2 контрактом; они не выдуманы. Existing storage witness этих desktop
полей тоже не раскрывает. Дополнительная Rust instrumentation/build для найденной
причины не нужна. При новом admission-only RED понадобился бы отдельный bounded
proposal: test-only closed booleans admission predicate + request/revision/phase,
без paths/keys/payload, guarded callback exact frozen142; сейчас не запускался.

Отдельный ошибочный normalUI ввод абсолютного имени run2 request2 дал
`maintenance_copy_unsafe_path`, а не busy. Этот случай сохранён и не засчитан
за корректную попытку. Для GREEN использованы breadcrumb и basename.
