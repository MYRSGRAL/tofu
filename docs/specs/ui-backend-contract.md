# Контракт выбранного экрана А с desktop backend

Вариант А утверждён пользователем в [направлении UI](ui-direction.md).
Этот документ задаёт перенос существующих действий на новый экран, независимо
от выбора Qt Quick, GTK4 или Slint. Он не подтверждает готовность native GUI.
Источник текущего протокола — `crates/yonik-desktop/src/backend.rs`;
JSON-команды передаются `DesktopHost::dispatch`, snapshots приходят callback.
БД, подписки и сессия принадлежат backend thread, UI не читает хранилище напрямую.

## Главный экран

На главном экране остаются выбранный сервер, одна основная кнопка, статус и
шестерёнка. Поля ядра/порта/URL проверки, обновление источников, диагностика и
будущие TUN/DNS/Fake-IP/kill switch находятся в настройках.

| Условие snapshot | Кнопка и карточка |
| --- | --- |
| `closed=true` | Команды больше не отправляются; действуют правила завершения host |
| `ready=false` | Подключение недоступно, показывается инициализация или ошибка старта |
| `ready && can_stop` | Основное действие отправляет `stop`; карточка показывает `active_name`, а не новый выбор |
| `ready && !can_stop && can_connect` | Действие `connect`, карточка показывает `selected_name` |
| Нет активной сессии и выбранного профиля | Карточка предлагает открыть выбор сервера; подключение недоступно |
| Остальные случаи | Подключение недоступно, причина берётся из состояния; недоступность не означает успешное соединение |

`can_connect` вычисляется backend из наличия выбранного профиля, отсутствия
активной сессии, фоновой операции и pending refresh review. Он не является
проверкой установленного ядра: `engine_missing` может появиться при подключении.
`busy` относится к работе с хранилищем/подпиской, а не заменяет lifecycle сессии.
Кнопка остановки не блокируется из-за `busy`, если backend оставляет `can_stop`.
Не выводить права действий только из строки `status`.

Названия профилей и источников считаются непроверенным пользовательским текстом:
plain text, без HTML/разметки, исполнения ссылок и управляющих последовательностей.
`selected_name` — выбор для следующего подключения; `active_name/active_engine`
фиксируют уже запущенную сессию и не подменяются при просмотре другого профиля.
`engine` — выбор следующего ядра, отдельного `prepared_engine` в DTO нет.

В текущем DTO нет достоверной страны/города выхода. Флаг/локация из демонстрации
не превращается в результат IP-геолокации. До появления явных данных карточка
использует название профиля и нейтральный значок; автоматический внешний
геозапрос ради главного экрана не добавляется. Аналогично, «лучшие серверы» и
неизмеренная задержка не изображаются как реальные результаты.

## Подключение и ошибки

| `status` | Смысл для пользователя |
| --- | --- |
| `Disconnected` | Активного локального proxy нет |
| `Preparing` | Подготовка подключения; `stop` служит отменой |
| `Starting` | Строка поддерживается текущим UI, но backend пока не публикует отдельную такую фазу |
| `Checking` | Ядро запущено, HTTPS-доступ ещё проверяется; успех не объявлен |
| `Connected` | Есть подтверждённый текущей проверкой HTTPS-доступ через SOCKS; это не гарантия TUN/system proxy |
| `Limited` | Ядро остаётся запущенным, актуального подтверждения доступа нет |
| `Stopping` | Идёт остановка; наличие действия определяется `can_stop` |
| `CleanupError` | Очистка не подтверждена; при доступном `can_stop` повторяется `stop` |
| `Error` | Подключение не удалось; подробность берётся из `error` |
| Неизвестная строка | Нейтральное неизвестное состояние, без зелёного успеха и выдуманной capability |

`stop` — приоритетная отмена сессии, refresh и TCP; отдельной универсальной
команды `cancel` нет. `cancel_tcp` относится только к TCP и не отключает proxy.
Интерфейс не должен называть `stop` безобидной отменой одного обновления, когда
активна сессия. `CleanupError` нельзя рисовать как безопасное отключение.

`error` — последний код snapshot, а не журнал или acknowledgement конкретного
запроса; следующая команда может его сбросить. UI переводит известные коды в
короткие сообщения, для неизвестного показывает общий текст без raw JSON,
credentials или содержимого профиля. После смены сети прежний HTTPS proof может
быть инвалидирован с переходом в `Limited` при сохранении работающего ядра.

`probe_result` и `tcp_result` имеют разную семантику. Первый описывает HTTPS/TLS,
HTTP-статус и время запроса через выбранный outbound, второй — отдельную TCP
проверку endpoint. `connect_ms` — медиана трёх успешных проб к одному адресу;
`samples_ms` и `samples_requested` показывают полноту серии, `selected_address`
фиксирует выигравший IP/порт/scope. Частичная или отменённая серия не имеет
медианы; DNS выполняется один раз. TCP latency не является скоростью VPN или доказательством
HTTPS-доступа. Полная диагностика доступна в настройках по действию пользователя;
на главном экране остаются короткий статус и причина ограничения.

## Навигация, настройки и выбор сервера

Главный экран содержит карточку сервера, кнопку подключения и статус.
Карточка открывает «Серверы», шестерёнка справа сверху — «Настройки».
Кнопка «Назад» и Escape поднимают на предыдущий уровень: подраздел настроек →
корень настроек → экран, из которого они открыты; «Серверы» → главный экран.
Постоянной строки вкладок, нижних кнопок импорта/выбора, бейджа SOCKS5 и
сводки подписки на главном экране нет. Адрес прокси доступен в настройках.
Начальное окно — 420×760, минимум — 380×600 логических пикселей. Управление
подписками и профилями объединено в «Серверах»; диагностика, интерфейс и
сведения о сборке открываются внутри «Настроек».

- Подключение: `set_engine`, копирование `listen_address`, выбранный engine и текущий режим
  локального SOCKS. Изменения относятся к следующей сессии, а не к работающему
  listener. Пока сессия активна или очистка не подтверждена, параметры не меняются.
- Серверы / подписки: `import_source` сохраняет/выбирает источник и сразу запускает загрузку;
  `add_source` сохраняет прежнее действие без загрузки для совместимости API.
  Также доступны `select_source`, `source_page`, `refresh`,
  `approve_refresh`, `discard_refresh`, `review_page`, `rename_source`,
  `delete_source`, `cancel_refresh`. Удаление требует подтверждения; отмена
  адресована текущей загрузке по source ID и токену, чтобы не отменить следующую.
  Review импорта остаётся
  отдельным явным действием. Неподдерживаемый proxy-fetch не заменяется скрытым DIRECT.
- Диагностика: `set_probe_target`, `reset_probe_target`, `check_tcp`, `cancel_tcp`.
  Поле URL после отправки очищается: snapshot намеренно содержит `probe_custom`
  и ожидаемый статус, но не возвращает URL с возможным секретом.
- Защита и маршрутизация: будущие режимы показываются как недоступные до
  подтверждённой capability. Настройка kill switch не подменяет applied-защиту.
- Выбор сервера: `query` с поиском и offset, `select_profile` с актуальной
  revision. Элементов управления избранным в текущем GUI нет; библиотечное
  избранное и совместимые backend-команды не являются функцией экрана. Страницы ограничены 200, список
  виртуализируется. `sort=name` существует только в benchmark, не в DesktopHost.

Backend-команда локального порта: `{"command":"set_listen_port","port":10808}`.
Допустимы только целые 1…65535; ноль, другие типы и лишние поля отклоняются
синхронно как `invalid_input`. При `can_stop=true` возвращается `busy`, прежний
порт сохраняется, включая `CleanupError`. Применение не проверяет занятость порта
и не открывает listener; bind выполняется при следующем подключении.
`reload` сохраняет настройку текущего host. Команда оставлена для API/диагностики,
пользовательского поля порта в GUI нет. Без override ОС выбирает порт и проверяет
TCP/UDP loopback; при коллизии перед Connect автоматический режим выбирает другой.
После preflight сохраняется гонка до фактического bind ядром.

Ядро, локальный порт, URL проверки и язык этого этапа ещё не имеют постоянного
хранилища GUI preferences. Эти настройки явно действуют в текущем сеансе.
Источники и библиотечное избранное сохраняются отдельно в уже существующей БД.
Legacy-имена каталога `tofu`, Secret Service attributes и криптографических domains
сохраняются ради совместимости зашифрованного хранилища и не служат UI-брендом.
Пользовательская диагностическая строка не должна превращаться в сериализованный
секрет в журналах, screenshot evidence или репозитории.

## Приёмка переноса

После выбора toolkit проверить реальное отображение DTO и действия в фазах
подготовки, проверки, успеха, ограничения, остановки и ошибки очистки. Отдельно:
отсутствие профилей/ядра, смена выбранного профиля во время активной сессии,
последняя ошибка, неизвестные коды, потеря сети, клавиатура/focus и доступ к
настройкам. Headless unit tests backend не заменяют проверку пикселей, renderer,
виртуализации, accessibility, scaling и tray lifecycle.
