# tofu — решения и открытые вопросы

Проект [tofu](README.md) развивается с открытым исходным кодом (open source). Linux — первая платформа, Android — следующий этап.

## ADR-001. Общая логика и платформенные оболочки

**Статус:** предложено по требованию переносимости.

Rust domain/application переиспользуется Linux и Android. Альтернатива — форк desktop GUI с копированием логики — повышает стоимость Android и расхождений правил. Linux/Android не делят OS API и UI, но делят бизнес-модель и её тесты. Собственный packet engine не создаётся.

## ADR-002. Два доступных ядра, одно основное подключение

**Статус:** рабочее предложение, одновременный каскад пользователь не запрашивал.

Xray и sing-box выбираются для профиля. Одно основное ядро владеет TUN-сессией. Альтернатива — постоянная связка sing-box для TUN плюс Xray для transport — повышает число runtime, сложность DNS и расход памяти. Она рассматривается только при подтверждённой несовместимости прямого варианта, с явным пересмотром бюджета.

Временные проверки серверов другого ядра допускаются в ограниченном probe-host без второго TUN.

## ADR-003. Android: отдельные native-исполнители

**Статус:** предложено, зависит от G-ANDROID.

VpnService/controller и один выбранный engine worker. Это обеспечивает один независимый Go runtime на процесс и понятное освобождение runtime при переключении. Цена — дополнительный процесс и защита socket FD через Binder.

Альтернативы: единый совместно собранный Go-артефакт для двух ядер; полный перезапуск одного VPN-процесса при смене загруженной библиотеки. Первый требует собственной Go-интеграции и согласования зависимостей, второй усложняет always-on/lifecycle. Выбор пересматривается только по результатам прототипа и измерений; собственный Go-код сейчас не запрашивался.

## ADR-004. Приватные VPN

**Статус:** цель Linux подтверждена пользователем, Android-эквивалент предложен.

Linux сохраняет внешние WG/другие VPN для приватных сетей. За ними остаются свои CIDR и внутренний DNS. Полноценный внешний full-tunnel VPN не входит в согласованный сценарий.

Android предлагает встроенный обычный WG-профиль в выбранном ядре. Он не обещает одновременную работу нашего VpnService с чужим и не заменяет управление mesh-VPN. Перед Android-реализацией пользователь должен подтвердить, что встроенный WG покрывает его потребность.

## ADR-005. GUI не определяет архитектуру ядра

**Статус:** выбор открыт по просьбе обсуждать UI отдельно.

Qt Quick/QML + CXX-Qt — предварительный фаворит для desktop-интеграции, с ценой Rust/C++ bridge и системных зависимостей. Slint — альтернативная прямая интеграция Rust и декларативный UI, с проверкой зрелости нужных desktop-возможностей. Iced не выбран; его актуальные улучшения не считаются достаточным доказательством пригодности без G-UI.

Android UI не обязан использовать toolkit Linux. Его выбор не требует менять domain/application. Макеты в стиле INCY будут отдельным документом после обсуждения.

## ADR-006. Режим отказа

**Статус:** предложение, требуется решение до реализации сетевой политики.

Для v1 предлагается возвращать обычную публичную сеть после окончательной остановки и явно уведомлять о сбое. Альтернатива — kill switch, сохраняющий блокировку публичного трафика с исключениями для LAN/приватных сетей.

Поведение влияет на firewall, recovery и критерии приёмки, поэтому не скрывается внутри слова «безопасно». При активной управляемой сессии, восстановлении и смене ядра исчезновение приватного VPN не разрешает отправку его адресов публичному proxy или внутренних DNS-зон публичному resolver. Полное отключение, включая окончательную остановку после исчерпания повторов, снимает сетевую политику клиента. Сохранённый пресет не оставляет постоянный firewall. Ошибка очистки — отдельное состояние с учётом оставшихся ресурсов; подробности в [сетевом контракте](networking.md).

## ADR-007. Версии и обновления

**Статус:** предложение.

Версии ядер фиксируются в совместимом manifest. Linux обновляет их доверенным механизмом, Android — вместе с APK. Обновления подписок и правил независимы от обновления исполняемого кода. Начальные версии-кандидаты указаны в sources.md; это не готовый compatibility manifest.

## ADR-008. Статистика и фон

**Статус:** предложение для выполнения требования энергоэффективности.

Проверки серверов ручные по умолчанию; фоновые обновления объединяются; UI подписывается только на нужные данные. Предложенные лимиты и бюджеты измеряются относительно engine-only baseline. Постоянный polling или запуск обоих основных ядер ради красивого списка не принимаются без отдельной функции и бюджета.

## ADR-009. Трей и два редактора одной политики

**Статус:** наличие функций подтверждено пользователем; детали поведения предложены в [отдельном контракте](routing-and-tray.md).

Linux должен полноценно работать из трея. Простой и расширенный режимы меняют представление одной RoutingPolicy; скрытые составные правила сохраняются и остаются видимыми в диагностике. Приложения и процессы входят в обязательный объём первой версии вместе с доменами/IP.

Предпочтительны нативные process-правила выбранного ядра. Альтернатива — внешний Linux-классификатор — добавляет права и стоимость, поэтому не принимается до провала G-APP и отдельного пересмотра архитектуры. Для GUI проверка трея и отсутствие фоновых redraw обязательны; процессная топология desktop-host выбирается по измерениям.

## ADR-010. tofu и открытый исходный код

**Статус:** название **tofu** и модель **open source** подтверждены пользователем. В репозитории уже размещён [текст GNU GPL v3.0](../../LICENSE); вариант SPDX и notices зависимостей уточняются перед поставкой.

Каноническое написание — tofu строчными буквами: имя продукта, репозитория и документации. Открываются собственные исходники, тесты, инструкции сборки и документация. Публикация репозитория/релизов — отдельное действие; этим документом она не выполнена.

Рекомендация для собственного кода tofu — **GNU GPL v3 или более поздняя версия**, идентификатор `GPL-3.0-or-later`. Она соответствует намерению сохранять открытость распространяемых производных версий: получатели должны иметь предусмотренный лицензией доступ к соответствующим исходникам и права на них. Это не требование публиковать каждую частную локальную правку. См. [условия GPLv3](https://choosealicense.com/licenses/gpl-3.0/).

У выбранных ядер разные условия: [sing-box 1.14.4](https://github.com/SagerNet/sing-box/blob/v1.14.4/LICENSE) использует GPLv3-or-later с отдельным уведомлением о названии/ассоциации, [Xray-core 26.10.31](https://github.com/XTLS/Xray-core/blob/v26.10.31/LICENSE) — MPL 2.0. Для tofu рекомендуется собственное название без представления проекта официальным продуктом этих авторов. Исходные лицензии и notices не заменяются лицензией tofu; совместимость конкретной поставки, native wrappers и GUI проверяется до распространения.

Наличие внешнего процесса и включение библиотеки в программу — разные интеграции; сама эта рекомендация не доказывает лицензионную совместимость любого варианта. В корне репозитория уже есть LICENSE с текстом GNU GPL v3.0. Ранее предложенный вариант GPL-3.0-or-later требует отдельного явного закрепления; наличие стандартного текста GPLv3 само по себе не фиксирует этот выбор.

| --- | --- | --- | --- |
| O-01 | GUI Linux и визуальный дизайн | Qt Quick/CXX-Qt или Slint; отдельно от ядра | Перед реализацией UI |
| O-02 | Fail-open или kill switch | Восстановление публичной сети с уведомлением | Перед сетевым прототипом и фиксацией UX отказа |
| O-03 | Обязательные протоколы/транспорты импортера | Начальный список в data-and-contracts.md | Перед реализацией парсеров |

| O-05 | Полный native JSON | Сохранение исходника, управляемый импорт; ограничения активации явно | Перед завершением импортера |
| O-06 | DNS-менеджер целевого Linux | Первая интеграция systemd-resolved | Проверить систему перед G-LINUX |
| O-07 | Android minSdk и устройства | arm64 первым, точный API после проверки native-зависимостей | Перед G-ANDROID |
| O-08 | Android private-WG вместо соседнего VPN | Встроенный обычный WG-профиль | Перед Android-продуктом |
| O-09 | Вариант SPDX и лицензионные уведомления tofu | LICENSE с GNU GPL v3.0 уже в репозитории; предложение or-later пока отдельно не закреплено | Уточнить SPDX/уведомления и условия зависимостей перед поставкой |
| O-10 | Охват нестандартных упаковок и селекторов процессов | Обязательный baseline: обычные Linux-приложения и проверенные executable/process-правила; AppImage/Flatpak/Wine и PID/cgroup — по подтверждённым capabilities | Перед фиксацией результата G-APP; ограничения не должны скрывать провал обязательного baseline |

Эти вопросы не мешают закончить документацию. Они не разрешают начинать реализацию или менять системную сеть. Следующий содержательный вопрос пользователю — O-02, потому что он меняет поведение при обрыве, а не косметику UI.
