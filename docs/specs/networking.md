# tofu — TUN, DNS и маршрутизация

Проект [tofu](README.md) развивается с открытым исходным кодом (open source). Linux — первая платформа, Android — следующий этап.

## 1. Исходная модель

Linux v1 обслуживает весь выбранный пользовательский трафик через один TUN и одно основное прокси-ядро. WireGuard/другой существующий VPN используется только для приватных сетей. Управление этим VPN остаётся у его приложения или системного менеджера.

В Xray-core 26.10.31 уже есть собственный [TUN inbound](https://github.com/XTLS/Xray-core/blob/v26.10.31/proxy/tun/README.md). У sing-box есть [TUN с маршрутизацией и исключениями](https://sing-box.sagernet.org/configuration/inbound/tun/). Поэтому третье ядро или постоянная цепочка sing-box → Xray не принимаются как обязательная часть решения. Работоспособность каждой комбинации TUN/DNS подтверждает отдельный прототип.

Системными изменениями владеет Linux network-adapter. Если часть операций делегируется автоматике ядра, они включаются в тот же журнал владения и не дублируются собственными правилами. Выбор между auto-route и внешним управлением — результат проверки адаптера, а не произвольная настройка пользователя.

## 2. Приоритеты

Предлагаемый порядок для управляемого профиля:

1. Служебные исключения от зацикливания: транспорт ядра, bootstrap DNS, локальный IPC. Эти исключения не означают разрешение произвольного трафика вне выбранной политики.
2. Зарезервированные приватные сети и внутренние домены VPN: через соответствующий VPN, либо блокировка при его отсутствии.
3. Реально подключённая LAN, loopback и нужное локальное обнаружение.
4. Личные правила пользователя по приложениям/процессам и назначениям в одном явно показанном порядке.
5. Включённые внешние наборы, включая ru-direct.
6. Действие по умолчанию: через выбранный прокси-сервер.

Изменение порядка личных правил допустимо; служебные инварианты выделены отдельно. Пересекающиеся правила показываются диагностикой с указанием победившего правила и его источника.

Для доменов поддерживаются точное совпадение и суффикс с границей DNS-метки: `example.test` не совпадает с `notexample.test`. Нормализация IDNA и регистра выполняется одинаково для обоих компиляторов. Регулярные выражения и скрипты не входят в начальный редактор правил.

Для IP используются канонические IPv4/IPv6-префиксы. Приоритет задаётся политикой, а не случайным порядком загруженных файлов. Приложение не разворачивает подсеть в список отдельных адресов.

Условие приложения/процесса ограничивает источник потока, а домен/IP — назначение; отдельного неявного слоя приоритетов для программ нет. Правило «программа И подсеть» совпадает только при выполнении обоих условий. Если условие источника уже ложно, реальное разрешение имени только ради CIDR этого правила не требуется. Поведение при неизвестном владельце, видимость конфликтов и простой/расширенный режимы заданы в [контракте редактора](routing-and-tray.md). Эти правила не обходят служебные исключения и защиту приватных сетей.

## 3. Приватные VPN и LAN

«Напрямую» внутри прокси-ядра и исключение из захвата TUN различаются. Для внешнего WireGuard нужно сохранить путь через его интерфейс и таблицу маршрутизации. Простого `DIRECT` может быть недостаточно, особенно если исходящие соединения ядра привязаны к физическому интерфейсу.

Network-adapter наблюдает за интерфейсами, адресами, маршрутами и policy rules через события ОС. Проверяет фактический маршрут к нужному адресу, а не только имя `wg0`. В пределах управляемой сессии явно сохранённый приватный префикс остаётся защищённым и после исчезновения интерфейса: система не должна отправлять его в публичный прокси или физический default route. Срок действия этой защиты определён в разделе 8.

Поддерживаются два источника приватных сетей:

- обнаруженные маршруты активного VPN, подтверждённые пользователем для постоянного пресета;
- вручную заданные CIDR, внутренние DNS-суффиксы и привязка к VPN.

Автообнаружение не гарантирует распознавания всех сторонних VPN. Для нестандартной маршрутизации предусмотрен явный пресет. При неоднозначном маршруте или конфликте адресных пространств подключение показывает конфликт и не пытается угадать безопасную сеть.

LAN определяется по реальным маршрутам и настройкам; постоянное исключение всего `10.0.0.0/8` не заменяет обнаружение локалки. Loopback, link-local, DHCP, IPv6 ND и mDNS учитываются отдельно от публичных адресов. Проверяются SSH, веб-интерфейс роутера, принтер/NAS и обнаружение `.local`.

WireGuard должен работать при обоих порядках включения: до нашего клиента и после. При его переподключении адаптер обновляет собственные исключения. При остановке нашего клиента удаляются только принадлежащие ему интерфейсы, правила и DNS-настройки. Чужие firewall rules и маршруты не очищаются.

## 4. DNS-политика

Одна общая модель описывает:

- bootstrap для адреса прокси-сервера, источников конфигурации и DNS-сервера;
- реальные DNS-ответы для прямых назначений;
- Fake DNS для выбранных проксируемых доменов;
- внутренние DNS-серверы/домены приватных VPN;
- исключения для LAN, `.local`, внутренних имён и пользовательских доменов;
- поведение IPv6 и недоступного DNS.

Bootstrap должен работать до появления TUN и не зависеть от подключения, которое он помогает установить. Выбор upstream и его способа доступа сохраняется явно. Реальные DNS-запросы проксируемых доменов не должны молча переходить на системный resolver при ошибке защищённого пути.

На Linux первая поддерживаемая интеграция — systemd-resolved с DNS по интерфейсам и суффиксам. Он поддерживает [маршрутизацию DNS для VPN](https://systemd.io/RESOLVED-VPNS/). Внутренние зоны идут к DNS соответствующего VPN; публичная политика клиента применяется к остальным запросам. NetworkManager может быть источником этих настроек. Его наличие не означает, что resolved действительно управляет DNS.

Если resolved отсутствует или не используется, v1 не подменяет `/etc/resolv.conf` вслепую: интерфейс сообщает ограничение управляемого TUN/DNS и сохраняет дополнительный локальный прокси-режим. Поддержка альтернативных resolver-менеджеров — отдельный адаптер. Перед реализацией необходимо проверить фактическую DNS-схему целевой CachyOS-системы.

Для скрытых внутри приложений DoH-запросов нельзя обещать полное доменное управление: такой трафик может обходить DNS клиента, а ECH/QUIC ограничивать получение имени через sniffing. В документации пользователя описывается этот предел и диагностика; перехват TLS не планируется.

## 5. Fake DNS / Fake-IP

Пользовательская настройка едина, но генераторы различаются: [FakeDNS Xray](https://xtls.github.io/en/config/fakedns.html) и [FakeIP sing-box](https://sing-box.sagernet.org/configuration/dns/server/fakeip/). Это функциональный аналог желаемого поведения Clash Verge, а не импорт его YAML-настроек.

Рабочее предложение — включать Fake DNS в управляемом TUN-профиле для проксируемых доменов. Приватные/LAN-зоны получают реальные ответы через свой resolver. Список исключений редактируется пользователем.

Проверяемые инварианты:

1. Выданный fake-адрес всегда возвращается выбранному ядру и не попадает в внешний WG или физическую сеть.
2. Диапазоны fake-адресов проверяются на пересечение с реальными маршрутами. Конфликт устраняется выбором другого поддерживаемого пула либо отказом включения режима.
3. Соответствие домен ↔ fake-адрес принадлежит конкретной engine-session. Нельзя передать старый адрес новому ядру и считать его значение прежним.
4. При остановке/смене ядра обновляется системный DNS-кэш и завершается старая сессия. Кэши отдельных приложений могут сохраниться; требуется проверка коротких TTL и понятное восстановление, а не обещание полного сброса всех приложений.
5. Восстановление persistent-кэша допускается только для того же ядра и совместимого формата/пула. Чужой кэш не конвертируется без явной реализации.

### Совместное решение доменных и CIDR-правил

Ниже — предлагаемый общий контракт, который должен пройти G-DNS для обоих ядер. Выдача fake-IP сохраняет имя, но сама по себе не закрепляет окончательное действие «прокси». Перед отправкой соединения проверяются все правила, которые могут победить по приоритету из раздела 2. Fake-IP никогда не сравнивается с реальными CIDR назначения.

| Ситуация | Реальное разрешение и путь DNS | Решение |
| --- | --- | --- |
| Назначение уже задано реальным IP | Не требуется для CIDR; sniffing не меняет фактический адрес | Правила применяются к этому адресу и доступному имени в общем порядке |
| Имя относится к сохранённой внутренней зоне | Только resolver соответствующего VPN | Приватный путь имеет приоритет; отсутствие VPN/resolver даёт отказ без публичного DNS fallback |
| Перед подходящим доменным правилом есть ещё не проверенное CIDR-правило | Обязательно; внутренние зоны разрешаются через VPN, остальные — через явно заданный реальный policy-resolver, по умолчанию через выбранный прокси | Сначала проверяется старшее CIDR-правило; личное доменное «прокси» не обходит более старший приватный CIDR |
| Подходящее доменное правило не имеет нерешённых CIDR-условий выше себя | Для выбора действия не требуется; последующее разрешение для соединения следует DNS-политике | Доменное правило может решить маршрут сразу; для прокси допустим Fake DNS |
| Несколько публичных A/AAAA соответствуют разным обычным правилам | Используется один актуальный набор ответов для разрешённых семейств IP | CIDR-правило совпадает, если ему соответствует хотя бы один адрес; побеждает первое правило в общем порядке, одно действие применяется ко всему соединению |
| Ответ смешивает защищённые приватные адреса с публичными либо адреса разных приватных VPN | Публичное повторное разрешение не исправляет конфликт | Отказ `DNS_POLICY_AMBIGUOUS`; диагностика требует однозначного приватного DNS/пресета, произвольный адрес не выбирается |
| Обязательное реальное разрешение завершилось ошибкой | Повтор допустим только в пределах заданного resolver-пути и бюджета | Отказ `DNS_POLICY_UNRESOLVED`, без перехода к младшему доменному правилу, DIRECT или системному resolver |

Один набор A/AAAA означает ответы разрешённых политикой семейств, связанные с актуальными TTL и поколением DNS/сети. Отсутствие записи одного семейства не равно timeout этого запроса. Если неполный ответ не позволяет исключить более приоритетное правило, применяется отказ разрешения. Изменение сети, resolver или приватного пресета инвалидирует соответствующее решение. Для буквального IP из соединения не подмешиваются другие адреса того же имени.

Для публичного набора правило «совпадение хотя бы одного адреса» намеренно может направить всё имя напрямую по одному подходящему ru-direct CIDR. Порядок адресов в DNS-ответе не меняет победителя; личное доменное правило выше ru-direct сохраняет приоритет. Это относится к доменному назначению, которое ещё требуется разрешить. Если приложение уже выбрало реальный IP, в том числе в TUN без Fake DNS, CIDR проверяется по этому IP: другой адрес того же имени не меняет решение. Диагностика указывает, был ли вход доменным или адресным; одинаковый результат двух ядер требуется при одинаковых входных данных.

Защищённые приватные назначения выделены отдельно: доступ допускается только к разрешённым адресам и через соответствующую сеть. Повторное локальное разрешение при соединении не должно обходить эту проверку. При передаче имени удалённому прокси клиент не контролирует его DNS; CIDR-политика описывает адреса, известные клиенту, и не обещает проверку удалённого resolver.

Policy-resolver возвращает реальные адреса и не обращается обратно к Fake DNS. Его транспорт и bootstrap заданы заранее; выбор DNS не вычисляется рекурсивно из ещё неизвестного адреса назначения. При включённой защите приватных CIDR реальные lookup могут потребоваться и для проксируемых имён. Кэширование ограничено TTL и поколением; Fake DNS не обещает устранить все DNS-запросы.

Это не утверждение об одинаковом поведении готовых ядер. У Xray `IPOnDemand` разрешает имя при встрече IP-условия, проверяет адреса по принципу «любой совпавший», но при ошибке использует исходный адрес и не меняет фактическое назначение: одного этого флага недостаточно для всего контракта. У sing-box существует отдельное действие `resolve`. См. [маршрутизацию Xray](https://xtls.github.io/en/config/routing.html) и [действия маршрутизации sing-box](https://sing-box.sagernet.org/configuration/route/rule_action/).

G-DNS должен доказать общий порядок, защиту приватных адресов и обработку ошибок на закреплённых версиях. Если нативными средствами адаптера контракт не выражается, capability сообщает неподдерживаемую комбинацию, а архитектура пересматривается до выпуска. Тихая подмена семантики или добавление собственного DNS/packet engine в Rust не считается выполнением этого этапа.

## 6. ru-direct и пресеты

Кандидат источника — [kyoresuas/ru-direct](https://github.com/kyoresuas/ru-direct): опубликованы доменные/IP-списки и форматы для обоих ядер. Источник нужно подтвердить, если пользователь имел в виду другой проект. Предлагаемый начальный уровень — standard; full выбирается явно из-за более широкого охвата.

Пресет хранит source-id, URL, формат, версию/хэш, дату проверки и режим включения. Загрузка идёт в staging, затем выполняются проверка размеров, разбор и проверка ядром. Публикуется один согласованный snapshot; не смешиваются домены от одного выпуска с IP от другого. При сетевой ошибке остаётся предыдущая версия, виден её возраст.

Пользовательские правила живут отдельно и имеют приоритет над скачанными наборами. Приложение скачивает данные; shell-скрипты настройки из внешних источников не исполняются. Контрольная сумма из того же источника проверяет целостность, но не заменяет доверие к издателю.

Предлагаемые независимо включаемые пресеты: «Локальная сеть», «Приватные сети VPN», «RU напрямую». Встроенный WG-профиль Android — отдельный тип источника приватной сети.

## 7. Проверки задержки

### TCP

Измеряется установление TCP-соединения до реального host:port выбранного сервера. Разрешение DNS учитывается отдельным этапом. Соединение закрывается сразу после проверки. Результат ничего не обещает о прохождении прокси-аутентификации и доступа к сайту.

Для транспорта, работающего только по UDP, TCP-проверка имеет статус «не применимо», а не «сервер недоступен». Она не заменяется скрыто на ICMP.

### Через сервер

Выполняется небольшой HTTPS-запрос через строго выбранный outbound. Проверка не должна уйти через системный прокси, ru-direct или соседний VPN из-за обычного правила. TCP до прокси, установка защищённого туннеля, TLS и ответ сайта образуют end-to-end задержку; это не измерение пропускной способности.

Стартовый URL: `https://www.gstatic.com/generate_204` — документированный [default URLTest sing-box](https://sing-box.sagernet.org/configuration/outbound/urltest/). Ожидается 204, TLS проверяется, редиректы по умолчанию не считаются успешным результатом. URL редактируемый; для собственного endpoint задаётся ожидаемый статус.

Ни один внешний endpoint не гарантирован постоянно. Ошибки различают DNS, соединение с сервером, туннель, TLS, timeout и неожиданный HTTP-статус. Повторная проверка другого URL запускается явно либо по выбранной политике; результаты разных endpoint не объединяются в один рейтинг.

Предлагаемый ручной режим: три последовательных измерения на сервер и медиана, фиксированный timeout, ограниченный параллелизм между серверами. Начальный быстрый проход может делать одно измерение с явной отметкой. Старые измерения сохраняют тип, endpoint, время и сеть, чтобы смена Wi-Fi не выглядела новым достоверным результатом.

## 8. IPv6, MTU и отказ

IPv6 поддерживается явным режимом: туннелировать либо контролируемо исключить/блокировать согласно настройке. Нельзя направить только IPv4 и молча оставить публичный IPv6 вне заявленного TUN-покрытия. Для LAN и приватных сетей IPv6 проверяется отдельно.

MTU выбирается адаптером консервативно с учётом нижележащего интерфейса; значение 9000 из примера документации не принимается автоматически. Тестируются крупные передачи, UDP, PMTU и сеть с меньшим MTU. Внешний WG переносит только приватный трафик и не должен случайно стать транспортом для публичного прокси.

Режим окончательного отказа определяется настройкой kill switch, как подтвердил пользователь: при включённом — сохранять блокировку публичного трафика, при выключенном — восстановить обычную сеть с уведомлением. Блокировка имеет собственного владельца/helper и applied-состояние; отключение kill switch/явное разблокирование снимает только её собственные ресурсы. Включённый пресет хранит намерение для следующего подключения и сам по себе не устанавливает постоянный firewall. Защита приватных CIDR и DNS-зон привязана к управляемой сессии:

| Состояние | Приватные CIDR и DNS-зоны | Владелец и завершение |
| --- | --- | --- |
| Подключение действует, включая закрытое окно UI | Доступ через соответствующий VPN; при его исчезновении — блокировка адресов и запрет публичного DNS fallback | Controller задаёт политику; helper учитывает и поддерживает собственные сетевые ресурсы |
| Временный сбой, восстановление или смена ядра | Защита сохраняется между попытками и поколениями; разрыв основного туннеля её не снимает | Helper удерживает защиту сессии до передачи новому поколению либо начала полной остановки |
| Повторы исчерпаны, принято решение окончательно остановиться | Сессионная защита сохраняется до демонтажа; при включённом kill switch публичная блокировка остаётся после остановки TUN, при выключенном восстанавливается обычная сеть | Переход через «Остановка» к «Ошибка» с явным статусом блокировки; helper учитывает сохранённые ресурсы, причина сбоя остаётся видимой |
| Явные «Отключить» / «Выйти и отключиться» | Сессионная защита снимается после остановки захвата; включённый kill switch отображается отдельно и снимается явным разблокированием | Остановка TUN не выдаётся за разблокирование сети; внешние VPN и их политика остаются под управлением своих владельцев |
| Очистка не завершена или helper недоступен | Фактическое покрытие неизвестно; возможны оставшиеся блокировки | «Ошибка очистки», перечень известных остатков и повторная сверка владения при восстановлении helper; нельзя заявлять полную очистку или гарантированную защиту |

Демонтаж сессионной защиты DNS-зон и приватных CIDR — финальный этап управляемой остановки после прекращения собственного захвата трафика. Снятие DNS и firewall не является одной атомарной операцией; при частичном результате фиксируются уже снятые и оставшиеся ресурсы. Обнаруженная потеря controller останавливает TUN с сохранением включённого kill switch; отдельный закрытый UI не считается потерей controller. При аварии helper исполнение политики и восстановление журнала проверяются отдельно, мгновенная успешная очистка либо блокировка не предполагается.

После снятия сессионной защиты за приватные назначения отвечает конфигурация ОС/внешнего VPN. Включённый kill switch — отдельная публичная политика с собственным владельцем и явным отключением, согласованными исключениями LAN/VPN и действием «разблокировать сеть». Если её фактическое применение не подтверждено, UI сообщает ошибку защиты и перечень известных ресурсов, не гарантирует блокировку по одному значению настройки.
