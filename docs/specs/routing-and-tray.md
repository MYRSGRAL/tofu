# yonik — трей и удобная настройка маршрутизации

Проект [yonik](README.md) развивается с открытым исходным кодом (open source). Linux — первая платформа, Android — следующий этап.

Работа в трее Linux, правила для отдельных приложений/процессов и простой/расширенный режимы добавлены пользователем в обязательный объём. Ниже описан предлагаемый контракт поведения. Внешний вид экранов и GUI toolkit по-прежнему обсуждаются отдельно.

## 1. Трей Linux

Закрытие основного окна по умолчанию скрывает его в трей и сохраняет подключение. Первый такой переход объясняет поведение один раз. Controller продолжает управлять сессией; открытие окна повторно подключает представление к существующему состоянию.

| Действие или событие | Поведение |
| --- | --- |
| Нажать значок | Открыть/поднять окно; повторный запуск не создаёт второй controller |
| Подключить / отключить | Та же команда и состояние, что в основном окне; отключение проходит полную сетевую очистку |
| Выбрать сервер | Открыть раздел «Серверы» с поиском и выбором профиля; смена применяется через controller |
| Открыть маршрутизацию / логи | Открыть соответствующий раздел; не держать его модель активной всё время |
| Выйти и отключиться | Остановить сессию, подтвердить очистку, завершить desktop-host; ошибка очистки остаётся доступной пользователю |
| Перезапуск Plasma или службы трея | Зарегистрировать значок заново по событию; подключение не перезапускается |
| Трей недоступен | Сохранить доступное окно управления; действие закрытия не должно незаметно прятать приложение без способа вернуть его |

Значок и короткое меню отражают состояния «отключено», «подключение», «подключено», «восстановление», «ошибка». Статус различим без опоры только на цвет. Текущие сервер и ядро доступны в подсказке; секретов и полных URL подписок там нет.

Трей не требует постоянно открытого renderer основного окна. Desktop-host может оставаться в том же UI-процессе либо иметь лёгкую отдельную роль — выбор зависит от toolkit и измерений. Общая библиотека Rust не импортирует GUI. Нет постоянной анимации значка, секундного таймера скорости и фонового сканирования серверов ради меню. Состояния приходят событиями; подробная статистика включается только для видимого потребителя.

Закрытие окна, команда отключения и выход из приложения — три разных действия. Автозапуск в трей и автоподключение остаются отдельными настройками, первоначально выключенными.

## 2. Одна политика, два представления

Простой и расширенный режимы редактируют одну `RoutingPolicy`. Переключение режима само по себе не меняет сеть, порядок правил или действие по умолчанию. Простой режим включён при первом запуске; это настройка представления, а не другое прокси-ядро.

Изменения сначала сохраняются как черновик. «Применить» показывает существенные изменения, проверяет возможности выбранного ядра и создаёт новое поколение плана. Ошибка оставляет предыдущее рабочее поколение. Новые правила действуют на новые соединения; существующие TCP/UDP-сессии не обещают мигрировать. Если адаптеру нужен перезапуск, это сообщается до применения.

Расширенные правила, которые нельзя выразить простой карточкой, сохраняются и продолжают действовать. Простой экран показывает их наличие и влияние на выбранный объект; просмотр и изменение открывают расширенный редактор. Переход в простой режим ничего не удаляет и не «упрощает» автоматически.

## 3. Простой режим

Основная операция: выбрать **приложение, запущенную программу, домен или IP/подсеть**, затем действие **«через прокси», «напрямую» или «блокировать»**. Для прокси используется текущий выбранный сервер. Отдельный сервер на каждое приложение пока не требуется.

- Приложения доступны по понятному имени и значку из desktop-каталога; поиск и выбор не требуют знания PID.
- Выбор из списка запущенных процессов помогает найти исполняемый файл. По умолчанию создаётся правило программы для её следующих запусков, что явно написано в форме.
- Адресная форма принимает домен, суффикс, IPv4/IPv6 и CIDR; пользователь не пишет JSON и маску вручную, если выбирает один IP.
- Пресеты LAN, приватного VPN и ru-direct представлены отдельными переключателями с кратким описанием.
- Поле «Остальной трафик» задаёт общее действие. Первоначально это прокси; сценарий «только выбранные приложения через прокси» получается явным выбором DIRECT для остальных и правилом proxy для нужных приложений.
- Карточка показывает применённое действие и конфликт с более приоритетным правилом. Добавление карточки не переставляет существующие правила незаметно.

Внутренние назначения VPN и служебные исключения сохраняют старший приоритет. «Приложение напрямую» не отправляет его рабочую приватную подсеть в физический default route. Порядок личных карточек соответствует порядку личных правил; новое правило добавляется в конец этой группы, пересечение показывается до применения.

## 4. Расширенный режим

Редактор показывает упорядоченную таблицу: включено, название, источник трафика, назначение, протокол/порт, действие, источник правила и диагностика. Пользователь может добавлять, дублировать, выключать и переставлять личные правила, не меняя служебные инварианты.

Условия разных групп соединяются через И: например, «этот исполняемый файл И этот домен И TCP/443». Несколько значений одной группы соединяются через ИЛИ. Условия домена и CIDR одновременно означают И и подчиняются общему DNS-контракту. Пустая группа означает любое значение; полностью пустое правило требует явного подтверждения широкого действия и диагностики перекрытых правил. Неограниченный язык выражений, Lua, произвольные скрипты и регулярные выражения не входят в исходный общий редактор.

Для источника доступны проверенные селекторы: точный путь исполняемого файла и, с предупреждением о совпадениях, имя процесса. UID, cgroup и правило для конкретного экземпляра допускаются только при отдельной подтверждённой capability, а не изображаются работающими универсальными полями.

PID в списке — диагностический атрибут, не постоянная идентичность. Нельзя сохранить `PID=1234` как правило на следующий запуск: номер может быть использован другой программой. Если позднее появится режим «только этот экземпляр», он привязан к идентичности процесса и времени его запуска, истекает при завершении и не подменяется правилом всех процессов с тем же именем.

Инструмент «Почему такой маршрут» принимает приложение/исполняемый файл и назначение, показывает первое сработавшее правило, его источник и необходимые DNS-данные. Предварительный расчёт отделён от наблюдённого маршрута реального соединения. Если владелец сокета или имя назначения неизвестны, результат не выдаётся за точное наблюдение.

## 5. Идентификация приложений в Linux

Desktop entry — источник имени, значка и данных запуска, а не достоверная метка каждого пакета. Идентификатор приложения связывается с проверенным набором исполняемых файлов, которые реально открывают сокеты. `Exec` разбирается как данные; helper не исполняет произвольные строки desktop-файлов. Формат определяется [Desktop Entry Specification](https://specifications.freedesktop.org/desktop-entry/latest/).

У браузеров, Electron-приложений и игр возможны дочерние сетевые процессы. Правило одного пути не получает автоматическое наследование по дереву процессов. Для wrappers, AppImage, Flatpak, Wine/Proton и программ на общем `python`/`java` требуется проверка фактического владельца соединения. Если приложение нельзя однозначно отличить от соседних, UI показывает ограничение и позволяет выбрать точный проверенный процесс, а не обещает охват по одному значку.

Запущенные процессы загружаются ограниченным снимком при открытии выбора, по ручному обновлению или поддерживаемым событиям. Скрытый экран не сканирует `/proc` по таймеру. Аргументы команд, environment и секреты не нужны каталогу. Сопоставление нового потока владельцу выполняет выбранное ядро/платформенный адаптер с ограниченным кэшем; пакеты не идут через Rust UI или IPC.

Если владелец конкретного потока неизвестен, процессное условие не считается совпавшим. Далее применяются обычные правила назначения и явное действие для остального трафика; UI показывает число/причину нераспознанных потоков. При режиме «остальные напрямую» это означает DIRECT и должно быть видно в настройке. Выборочное правило приложения не заявляется как универсальная граница безопасности. Если платформенные права/механизм распознавания недоступны целиком, активация политики с такими правилами отклоняется до применения вместо молчаливого игнорирования.

DNS-запрос, переданный приложением системному resolver, может принадлежать процессу resolver. Поэтому процессное правило трафика не означает отдельный DNS-путь этого приложения. Общая DNS-политика и защита внутренних зон сохраняются; обособленный DNS по приложениям требует доказуемой атрибуции и отдельной capability.

## 6. Два ядра

Основной вариант — нативные process-правила выбранного ядра. [Xray описывает `process`](https://xtls.github.io/en/config/routing.html) для имени и пути локального процесса; [sing-box описывает `process_name` и `process_path`](https://sing-box.sagernet.org/configuration/route/rule/) для Linux. Наличие полей не доказывает полноту распознавания в конкретном TUN, sandbox и privilege profile.

Компилятор сохраняет одну семантику правил и порядка для поддерживаемого общего подмножества. Различия выражаются в capabilities и ошибках, а не в скрытом запуске второго ядра. G-APP проверяет TCP/UDP, IPv4/IPv6, дочерние процессы, права и стоимость распознавания на закреплённых версиях.

Внешний классификатор на cgroup/eBPF/nftables — возможное отдельное архитектурное решение только при провале нативного варианта. Сейчас он не выбран: новые привилегии, охват уже запущенных приложений и расход ресурсов требуют самостоятельного доказательства. Сам факт выбора приложения не создаёт свой packet engine.

## 7. Будущий Android

Общие модели хранят платформенный тип идентичности: desktop application/executable на Linux и package identity на Android. Путь Linux не превращается в имя пакета автоматически. Импорт неподходящего селектора сохраняет правило, но отмечает его неприменимым до явного сопоставления; активная политика с необработанными правилами не включается незаметно.

У Android есть [списки приложений VpnService](https://developer.android.com/develop/connectivity/vpn): включать или исключать приложения из VPN можно на уровне ОС, изменение списка требует пересоздания VPN. Но исключение из захвата обходит наши правила назначения и защиту приватных сетей для этого приложения. Поэтому оно не является прозрачной реализацией действия DIRECT: основной вариант — захват приложения и маршрутизация внутри ядра с платформенной атрибуцией. Этот механизм проверяется отдельно для обоих native wrappers.

Пользовательский контракт «приложение → действие» переносим; PID, произвольные пути Linux и дерево чужих процессов — нет. Системный режим Android «блокировать без VPN» учитывается отдельно. На Android роль трея выполняют предусмотренные платформой уведомление и действия сервиса.
