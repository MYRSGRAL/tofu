# yonik — адаптеры Linux и Android

Проект [yonik](README.md) развивается с открытым исходным кодом (open source). Linux — первая платформа, Android — следующий этап.

## 1. Linux: процессы и права

Предлагается три роли:

1. **UI и пользовательский controller.** Обычный UID. UI может завершаться отдельно; controller живёт в пользовательской сессии и владеет моделями, подписками, хранилищем и состоянием.
2. **Сетевой helper.** Небольшой системный сервис с ограниченным набором команд, авторизацией через polkit и журналом принадлежащих ресурсов.
3. **Выбранное прокси-ядро.** Доверенный исполняемый файл в отдельной управляемой service/cgroup. Не получает полные права root по умолчанию; необходимые capability определяются прототипом TUN.

Рабочий вариант запуска — закреплённый systemd service template для ядра от выделенного системного пользователя с необходимыми сетевыми capability. Helper принимает типизированный план и выбирает путь ядра из собственного доверенного реестра. Из UI нельзя передать executable path, shell command, произвольную среду или systemd unit.

`CAP_NET_ADMIN` остаётся сильной привилегией. Она не превращает потенциально уязвимое ядро в безопасный sandbox. Поверх неё нужны доступ только к конфигу текущей сессии, ограниченный доступ к файлам, отсутствие пользовательского home и проверка применимости systemd hardening. Конкретный набор ограничений проверяется с обоими ядрами, а не копируется из примера сервиса.

Вариант с полностью непривилегированным ядром и передачей подготовленного TUN FD предпочтительнее, если конкретный desktop-runtime поддержит его без форка. Это отдельный проверяемый вариант G-LINUX, не обещание текущего CLI.

## 2. Linux: границы доверия

| Граница | Правило |
| --- | --- |
| UI → controller | Версионные команды; UID пользователя и принадлежащие ему профили |
| controller → helper | Системная авторизация, проверка peer credentials, лимиты, неизменяемый проверенный план |
| helper → engine | Только системно установленный доверенный бинарник, проверенный конфиг и ограниченный service profile |
| подписка → import | Только данные; ни команды, ни пути к исполняемым файлам |
| engine → логи/UI | Непроверенные строки, ограничение размера, очистка credentials и управляющих последовательностей |

Доверенная установка ядра не должна быть изменяема обычным пользователем перед привилегированным запуском. Поэтому произвольный бинарник из `~/.cache` нельзя повысить через helper. Ручной выбор внешнего ядра, если появится, будет отдельным непривилегированным режимом с ясными ограничениями.

Повторная авторизация и её срок зависят от действия и локальной политики polkit. Пароль не хранится приложением. Сетевой сервис не предоставляет универсальный интерфейс запуска команд.

## 3. Linux: сеть и восстановление

Каждая сессия получает собственные имена TUN, nftables table/chain, routing table/rule IDs и защищённый каталог в `/run`. Идентификаторы проверяются на занятость, а не считаются свободными потому, что совпадают с дефолтом ядра.

Журнал ресурсов содержит owner, session-id, generation и достаточное описание для проверки фактического состояния после сбоя. Удаление ресурса выполняется только при подтверждённом владении. Сбой одной очистки не скрывает остальные; результат содержит перечень оставшегося.

При потере controller helper сначала проверяет принадлежащие ему процессы/сессию, останавливает ядро и демонтирует сессионный захват трафика. Если kill switch включён, принадлежащая helper публичная блокировка сохраняется и учитывается отдельно от остановленного TUN; при выключенном kill switch восстанавливается обычная сеть. При закрытии UI controller остаётся, и подключение сохраняется. При перезапуске helper допускается только проверяемое восстановление учёта либо остановка осиротевшей сессии с соблюдением этой политики — не безусловное удаление чужого tun0. Недоступность helper означает неизвестное фактическое покрытие, а не подтверждённую блокировку или очистку.

Защита от ухода приватных назначений действует, пока клиент управляет сессией, включая ограниченное восстановление и смену ядра. При полной остановке сессионная защита приватных CIDR и DNS-зон снимается после прекращения собственного захвата; далее за приватные назначения отвечает конфигурация ОС/внешнего VPN. Включённый kill switch имеет отдельного владельца и applied-состояние: его публичная блокировка сохраняется после окончательного сбоя, остановки TUN и выхода до явного отключения/разблокирования. При выключенном kill switch обычная сеть восстанавливается. Сохранённый пресет сам по себе не устанавливает firewall. Ошибка очистки фиксирует уже снятые и оставшиеся ресурсы, а не успешную остановку. Состояния, согласованные исключения LAN/VPN и владение определены в [сетевом контракте](networking.md#8-ipv6-mtu-и-отказ).

Первые поддерживаемые условия: systemd, управляемый systemd-resolved, nftables и доступные TUN/Netlink. Пакет проверяет эти условия и показывает конкретное отсутствие возможности. Поддержка других DNS/network managers расширяется адаптерами.

## 4. Linux: упаковка и desktop-интеграция

Первый проверяемый пакет — Arch/CachyOS x86_64; целевой продукт должен работать на основных Linux-дистрибутивах и DE, не только KDE. Матрица включает KDE Plasma, GNOME и Xfce, Wayland и X11 с доступными backend; точные минимальные версии и форматы пакетов фиксируются при G-PACKAGE. Приложение имеет desktop entry, иконку, уведомления, трей и обработку повторного запуска.

Трей — обязательный способ работы Linux v1 там, где DE предоставляет host: закрытие окна сохраняет управление через значок, а полный выход останавливает TUN с учётом настройки kill switch. Desktop-host восстанавливает регистрацию после перезапуска tray-host по событию, не перезапуская engine. При отсутствии работающего трея, включая обычные GNOME-сессии без соответствующего host, окно не скрывается незаметно и состояние подключения остаётся явно доступно. Выбор toolkit должен пройти эти случаи на целевых DE; [контракт трея](routing-and-tray.md) независим от конкретной реализации.

Для выбора приложений Linux-host читает desktop-каталог и ограниченные сведения о запущенных процессах. Нативные process-правила ядра проверяются с реальными UID, TUN и service hardening. Наличие `CAP_NET_ADMIN` само по себе не доказывает доступность всех метаданных процессов; ради каталога нельзя автоматически выдавать полный root или неограниченный просмотр чужого `/proc`. Ошибка доступа становится ограничением capability, а не молчаливым пропуском правил.

AppImage не решает установку привилегированного сервиса и capabilities. Поэтому он не выбирается как единственный способ поставки. Flatpak требует отдельного решения host-helper и также не считается бесплатным следствием выбора GUI.

Обновление системного helper/ядра выполняется доверенным пакетным механизмом. Обновление пользовательских подписок/правил не требует привилегий. Qt Quick/CXX-Qt остаётся прототипом; GTK4 и Slint сравниваются по G-UI/G-POWER, упаковка проверяется отдельно от выбора toolkit.

## 5. Android: системные ограничения

У обычного Android в одном пользовательском профиле активен один `VpnService`. Поэтому внешнее приложение WireGuard нельзя просто оставить рядом с нашим TUN. Источник: [Android VPN](https://developer.android.com/develop/connectivity/vpn).

Предлагаемый будущий эквивалент доступа к приватным сетям — встроенный WG-профиль внутри выбранного engine: у sing-box есть [WireGuard endpoint](https://sing-box.sagernet.org/configuration/endpoint/wireguard/), у Xray — [WireGuard outbound](https://xtls.github.io/en/config/outbounds/wireguard.html). Совместная работа с основным прокси в одном TUN, внутренний DNS и диапазоны маршрутов требуют интеграционного теста. Это не заменяет управляющие серверы NetBird/Tailscale и не даёт совместимость с любым протоколом VPN.

Android не наследует Linux service, polkit, nftables, Netlink-политику или запись системного DNS. Платформа создаёт TUN через VpnService; native-ядро получает его дескриптор и callbacks. Сокеты выхода защищаются от попадания обратно в VPN через [VpnService.protect](https://developer.android.com/reference/android/net/VpnService), с учётом выбранной underlying network.

Правила приложений Android используют package/UID-атрибуцию платформы, не пути и PID Linux. VpnService allow/disallow lists управляют захватом целиком и не заменяют общий редактор «приложение + назначение»: исключённый пакет обходит нашу маршрутизацию. Переносимый контракт и ограничения описаны в [маршрутизации приложений](routing-and-tray.md); возможность атрибуции в обоих workers проверяется в G-ANDROID.

## 6. Android: интеграция двух ядер

Кандидаты native-интеграции: upstream libXray и `experimental/libbox` из закреплённой версии sing-box. [Интерфейс libbox 1.14.4](https://github.com/SagerNet/sing-box/blob/v1.14.4/experimental/libbox/platform.go) содержит создание TUN, управление исходящими сокетами и наблюдение за интерфейсами. [libXray](https://github.com/XTLS/libXray) предупреждает о нестабильности API и недопустимости двух независимо собранных Go runtime в одном процессе.

Предложенная исходная схема:

- UI-процесс общается с сервисом через типизированный Binder API и может быть уничтожен отдельно.
- Один `VpnService` в процессе `:vpn` содержит controller и общую Rust-библиотеку через UniFFI.
- Выбранное native-ядро работает в одном отдельном исполнительном процессе: `:engine_xray` либо `:engine_singbox`. Компоненты исполнителей не экспортируются наружу.
- Каждый исполнитель загружает только свою библиотеку с одним Go runtime. Неиспользуемый исполнитель не запускается; после остановки его процесс завершается в рамках собственного lifecycle, чтобы не удерживать невыгружаемый runtime.
- TUN FD передаётся исполнителю через `ParcelFileDescriptor`; пакеты далее идут прямо между дескриптором и native-ядром.

Процессы разделены ради гарантированного жизненного цикла двух native runtime, а не ради передачи пакетов по Binder. Дополнительная память `:vpn` + исполнитель учитывается в бюджете. Оптимизацию до единого native-артефакта можно рассматривать только после измерений и отдельного решения о собственной Go-интеграции; сейчас своего Go-кода не планируется.

### Защита сокетов и владение FD

Число FD имеет смысл только в своём процессе. Для вызова protect из `:vpn` исполнитель передаёт дубликат socket FD через Binder до connect. Сервис защищает полученный descriptor, возвращает результат и закрывает свою копию. Исходным сокетом продолжает владеть native-ядро. Ошибка или timeout защиты отменяют соединение; уход в незащищённый connect запрещён.

Это callback на создание сокета, а не на каждый пакет. Нельзя оборачивать его в общий lock, который одновременно нужен обработчику Binder: такой цикл создаст deadlock. Отдельно тестируются TCP, UDP, bootstrap DNS и reconnect.

Для TUN сервис владеет исходным ParcelFileDescriptor, исполнитель — переданным дубликатом, а библиотека может создавать ещё один. Контракт адаптера закрепляет владельца каждой копии и порядок закрытия. Нельзя закрывать исходный FD, полагаясь на недокументированное копирование библиотекой.

### Переключение ядра

Controller останавливает старого исполнителя, дожидается закрытия дескрипторов, завершает его процесс, очищает поколение состояния и запускает другого. Новый исполнитель не читает TUN до подтверждённой передачи владения. Если DNS-кэш или настройки TUN требуют нового интерфейса, VpnService пересоздаёт его. Возможен короткий разрыв; seamless handoff не обещается.

## 7. Android: фон, обновления и UI

Активное VPN-подключение обслуживает foreground service с видимым уведомлением. Закрытие Activity не останавливает его. Отзыв разрешения, always-on и потеря underlying network являются событиями состояния, а не поводом для бесконечного перезапуска.

Неактивные подписки/правила обновляются через разрешённые ОС окна фоновой работы с ограничениями сети/батареи. Постоянные wakelock, частые alarms и polling UI не являются нормальным режимом. Настройки never/always-on согласуются с системным поведением; ограничения пользователя «блокировать без VPN» учитываются отдельно.

Нативные библиотеки входят в APK/AAB для соответствующего ABI. Схема скачивания desktop-бинарника в каталог приложения и последующего exec не переносится: Android ограничивает [исполнение файлов из writable app home](https://developer.android.com/about/versions/10/behavior-changes-10#execute-permission). Обновление кода ядер выполняется с обновлением приложения; подписки и rule sets остаются данными.

Начальный Android ABI для будущего прототипа — arm64-v8a; дополнительные ABI и minSdk выбираются по устройствам и поддержке native-зависимостей. Эмулятор подходит для correctness, но не является доказательством малого расхода батареи.

## 8. Непроверенные интеграции, которые нельзя скрыть

- Разделённые исполнители, Binder-передача сокетов и TUN с конкретными libXray/libbox.
- Права Linux-ядра и возможность перенести больше сетевых операций в helper.
- DNS и Fake-IP после переключения движка, сна, смены сети и отзыва VPN-разрешения.
- WG + основной outbound в одном Android-ядре, внутренний DNS и keepalive.
- Переносимость/лицензирование пакета native-зависимостей.

Для них определены ранние проверочные этапы. Наличие соответствующего класса или опции в upstream не считается пройденным тестом продукта.

Визуальное направление и разделение главного экрана/настроек закреплены в
[требованиях к UI](ui-direction.md). Референс пользователя — тёмная палитра
highpriority.cloud и простой экран подключения; варианты показываются до переноса
в основной GUI.
