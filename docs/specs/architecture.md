# tofu — архитектура и стек

Проект [tofu](README.md) развивается с открытым исходным кодом (open source). Linux — первая платформа, Android — следующий этап.

Статус: предложенная архитектура. Зафиксированные требования отделены от выбора библиотек и непроверенных интеграций.

## 1. Рассмотренные подходы

| Подход | Сильная сторона | Ограничение | Решение |
| --- | --- | --- | --- |
| Форк desktop-клиента с общей логикой внутри GUI | Быстрый доступ к готовым экранам | Перенос Linux-интеграции и UI на Android потребует большого разделения | Не предлагается как основа |
| Общая Rust-библиотека и платформенные оболочки | Одни правила, импорт и состояние; естественные API каждой ОС | Нужно явно спроектировать границы и FFI | Рекомендованная основа |
| Одна универсальная оболочка и один способ запуска ядер везде | Меньше исходных экранов | Android VPN и нативные библиотеки существенно отличаются от Linux | Не принимать как предположение |

Общее ядро не должно зависеть от того, остаётся ли мобильное приложение в том же репозитории или развивается как форк.

## 2. Предложенный стек

| Слой | Предложение | Статус |
| --- | --- | --- |
| Модели, импорт, политики, компиляторы | Rust stable, типизированная сериализация Serde | Архитектурное предложение |
| Асинхронный контроллер | Tokio с выбранными feature-флагами; runtime создаёт host | Архитектурное предложение |
| Метаданные | SQLite с версиями схемы; секреты через отдельное хранилище | Архитектурное предложение |
| События/диагностика | Структурированные события и tracing, ограниченные буферы | Архитектурное предложение |
| Linux IPC | D-Bus через Rust-адаптер zbus | Архитектурное предложение |
| Linux сеть | Netlink, отдельные принадлежащие приложению правила nftables, resolved/NM-адаптер | Требует проверки на целевой системе |
| Linux UI | Qt Quick/CXX-Qt — прототип; GTK4/Slint — сравнение | Основные Linux DE, Wayland/X11, окончательный выбор по G-UI/G-POWER |
| Android host | Kotlin, VpnService, JNI-библиотеки ядер, UniFFI для Rust | Будущая платформа, обязательный интеграционный прототип |
| Android UI | Отдельная нативная оболочка | Пока не выбирается |

[Tokio](https://docs.rs/tokio/latest/tokio/) и [zbus](https://docs.rs/zbus/latest/zbus/) предоставляют нужные механизмы, но точные версии Rust-зависимостей фиксируются только при создании проекта. Сейчас lockfile не создаётся.

Qt Quick — предварительный кандидат при приоритете desktop-интеграции; Slint — при приоритете прямой связи UI с Rust. Переносимость бизнес-логики не зависит от этого решения. Технический пробный экран должен проверить кириллицу, ввод, буфер обмена, дробный масштаб Wayland, клавиатуру, трей и простой без перерисовки.

## 3. Границы компонентов

| Компонент | Ответственность | Чего внутри нет |
| --- | --- | --- |
| domain | Профили, серверы, правила, платформенно помеченные селекторы приложений, ограничения, события | Вызовов ОС/файловой системы, GUI, async-runtime |
| import | Локальный разбор URI/JSON/Base64, нормализация, отчёт | Скачивания, сетевых изменений, сторонних конвертеров |
| policy | Приоритеты правил источника/назначения, DNS-политика, приватные сети, объяснение решений | Прямого изменения маршрутов и собственного поиска владельца каждого пакета |
| compiler-xray / compiler-singbox | Типизированная генерация конфигурации закреплённой версии | Запуска процессов и доступа к UI |
| application | Команды, состояние подключения, поколения конфигураций, план задач | systemd, Android-классов, Qt |
| storage | Транзакции метаданных, миграции, ссылки на секреты | Секретов в логах и открытых backup |
| platform-linux | Привилегии, сеть, процессы, каталог приложений и наблюдение за окружением | Бизнес-правил, дублирующих policy |
| platform-android | Жизненный цикл ОС, TUN FD, защищённые сокеты, JNI | Другой реализации подписок и приоритетов |
| presentation | Окно/трей, два представления одной политики, снимки состояния, команды и переводы RU/EN | Запуска ядра напрямую и собственного DNS |

Это логические модули. Отдельные crates создаются по границам зависимости; микросервисов и репозитория на каждый модуль не требуется.

## 4. Управление и передача трафика

Команды проходят путь «UI → application → план → платформенный host → выбранное ядро». Обратно идут события состояния и агрегированная статистика.

Пакеты проходят путь «TUN → выбранное прокси-ядро → сеть». Rust application, D-Bus, UniFFI, Binder и UI не получают каждый пакет. Межъязыковая граница используется для настройки, управления и ограниченных порций событий.

Маршрутизация приложений использует нативную атрибуцию потока выбранного ядра/платформы. Rust получает каталог для выбора программы и компилирует селекторы, но не добавляет второй проход обработки пакетов. Стоимость определения владельца соединения входит в G-APP и G-POWER.

Основная сессия имеет один активный engine-id. Второе ядро допускается временно только для явно запрошенной проверки серверов без TUN, с отдельным бюджетом и гарантированной остановкой. На Android исполнители не загружают две независимо собранные Go-библиотеки в один процесс; подробности в [адаптерах](platforms.md).

## 5. Владение состоянием

Единственный application-controller владеет текущей сессией. UI может закрываться и подключаться повторно. Профиль, применённая конфигурация и доступность сети — разные сущности:

- desired — что выбрал пользователь;
- applied — какое поколение реально применено;
- observed — что сообщили ОС и ядро;
- persisted — последняя сохранённая подтверждённая конфигурация.

Изменение desired само по себе не означает успешного применения. Конфликтующие команды сериализуются. Каждая операция имеет request-id, generation и отмену. Позднее событие от остановленной сессии не меняет новое состояние.

На Linux закрытие окна оставляет доступный tray-host и controller. Значок получает события состояния; скрытые экраны отписываются от статистики. Простой и расширенный редакторы — представления одного desired-профиля; переключение представления не запускает Apply и не удаляет составные правила. Подробный контракт задан в [трее и маршрутизации](routing-and-tray.md).

## 6. Состояния сессии

| Состояние | Значение | Основные выходы |
| --- | --- | --- |
| Отключено | Наша сессия остановлена, очистка её сетевых ресурсов подтверждена | Подготовка |
| Подготовка | Проверка профиля, ресурсов, прав и сетевого плана | Запуск, Ошибка, Отключено |
| Запуск | Запуск ядра и применение сети | Проверка, Остановка |
| Проверка | Готовность ядра, DNS и контрольный запрос | Подключено, Ограниченная проверка, Восстановление |
| Подключено | Сессия готова, статус актуален | Перенастройка, Восстановление, Остановка |
| Ограниченная проверка | Ядро готово, тестовый endpoint не подтвердил доступность | Подключено, Восстановление, Остановка |
| Перенастройка | Переключение сервера/ядра или политики | Проверка, Остановка, восстановление старого поколения |
| Восстановление | Ограниченные повторы после смены сети/сбоя; приватная защита удерживается | Проверка, Остановка |
| Остановка | Прекращение задач и удаление только собственных ресурсов | Отключено, Ошибка с сохранённой причиной сбоя либо Ошибка очистки |
| Ошибка | Нужна настройка/действие; активных ресурсов сессии нет, причина сохранена | Подготовка |
| Ошибка очистки | Состав ресурсов сверяется; успешная остановка не подтверждена | Остановка после восстановления доступа к владельцу ресурсов |

Наличие процесса — недостаточное условие «подключено». Недоступность одного URL — недостаточное условие «сервер не работает».

## 7. Применение сетевого плана

1. Снять актуальное состояние сети, определить конфликтующие подсети, DNS и существующие VPN.
2. Скомпилировать новый план, проверить ограничения и конфигурацию ядра без применения.
3. Получить право на операцию и резервировать собственные идентификаторы/порты.
4. Подготовить исключения от зацикливания и приватные сети; запустить выбранный runtime с автоматическим системным routing/DNS под контролем адаптера.
5. Применить маршруты и DNS в предусмотренном адаптером порядке. Проверить готовность и записать applied-generation.
6. При ошибке выполнить обратные действия по журналу владения и вернуть последнее рабочее состояние, когда это возможно.

Единой атомарной транзакции для ядра, маршрутов и DNS нет. Каждый шаг имеет проверку результата и компенсирующее действие. Нельзя восстанавливать всю таблицу маршрутов или весь DNS из старого снимка: параллельно мог измениться внешний VPN.

Переключение основных ядер в v1 предполагает краткий разрыв соединений. Бесшовная миграция TCP-сессий между ними не обещается. Перед включением нового Fake DNS-пула требуется обработка старых кэшей по [сетевой политике](networking.md).

## 8. Переносимость проверяется до Android UI

Общие модули собираются для Android ABI, не импортируют platform-linux и проходят тесты с подставными часами, хранилищем и host. FFI работает с ограниченными DTO, идентификаторами и событиями, а не с Rust-объектами ОС. Схема экспортируемых профилей имеет собственную версию, независимую от версии приложения и прокси-ядра.

Общий код не хранит глобальный runtime. Linux-host и Android-host создают по одному runtime контроллера. Обработчики UI не вызывают блокирующий запуск процессов, DNS или SQL.

## 9. Предлагаемый порядок

Сначала подтвердить сеть и адаптеры двух ядер, затем реализовывать общую модель и управление, после этого — UI. Ранний Android-прототип проверяет FFI/TUN и разделение runtime; полноценный Android-клиент следует после Linux v1. Подробные результаты каждого этапа определены в [плане проверок](validation-and-roadmap.md).
