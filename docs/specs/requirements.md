# yonik — требования

Проект [yonik](README.md) развивается с открытым исходным кодом (open source). Linux — первая платформа, Android — следующий этап.

## 1. Назначение и терминология

Приложение управляет пользовательскими прокси-серверами и подписками. Собственный сервер, продажа подписок, облачная учётная запись и синхронизация не входят в первую версию.

**Ядро приложения** — наша переносимая библиотека Rust. **Прокси-ядро** — Xray-core или sing-box. **Профиль подключения** — выбранный сервер, ядро и набор сетевых политик. **Подписка** — источник серверов, который можно обновлять. **Пресет** — включаемый набор правил с известным источником и приоритетом.

FR-20 дополняет правила назначения FR-11: приложение/процесс — источник трафика, домен/IP/CIDR — назначение. Оба вида условий доступны совместно. Постоянное правило PID и все возможные sandbox/упаковки не считаются автоматически поддержанными; границы заданы в [контракте трея и маршрутизации](routing-and-tray.md).

## 3. Предложенный базовый набор удобств

Это рекомендации, дополняющие запрос, а не отдельные подтверждённые требования:

- Поиск и сортировка серверов, подключение одним действием; избранное в UI не требуется. Трей вынесен в обязательное FR-19.
- Автозапуск приложения и автоподключение как две отдельные настройки, первоначально выключенные.
- Показ текущего сервера, режима, состояния и краткой причины сбоя.
- Восстановление после сна и смены сети с ограниченными повторными попытками.
- Время последнего обновления подписки, трафик/срок действия, если источник предоставляет эти данные.
- Резервная копия настроек и диагностический экспорт; секреты включаются только в отдельную явно выбранную защищённую копию.
- Локальный SOCKS/HTTP-прокси как дополнительный режим Linux. Общесистемный прокси зависит от окружения и не равнозначен TUN.
- Проверка маршрута: почему конкретный домен/IP пошёл напрямую, в прокси либо в приватную сеть.

Kill switch — отдельная настройка: при окончательном сбое TUN включённый режим сохраняет блокировку публичного трафика, выключенный восстанавливает обычное подключение с уведомлением. Настройка и фактическое применение защиты отображаются раздельно; неподтверждённая блокировка не считается успешной. Подробности в [решениях](decisions.md) и [сетевом контракте](networking.md).

## 4. Пользовательские сценарии

### Первый запуск

Выбор RU/EN → импорт подписки/профиля → показ распознанных серверов и ошибок → выбор сервера → просмотр базовых сетевых настроек → подключение. Системная авторизация Linux нужна для сетевых изменений; окно работает без повышенных прав.

### Ежедневная работа

Выбор сервера из окна или трея. Закрытие окна при включённом подключении сохраняет подключение, статистика скрытых экранов останавливается. Команда «Выйти и отключиться» явно останавливает туннель и очищает собственную сеть. Приложение показывает «подключено» после готовности сети и проверки работоспособности; недоступность одного тестового сайта отражается как неполная проверка, а не доказанный отказ сервера.

### Правило для программы

Простой режим → выбрать приложение или запущенную программу → выбрать действие → увидеть охват и конфликтующие правила → применить. Для комбинации «программа + домен/подсеть + порт» открыть расширенный режим. Возврат в простой режим сохраняет составное правило и показывает его влияние. Сетевой результат можно объяснить через диагностику маршрута; неизвестная принадлежность потока не скрывается.

### Локалка и работа

Пользователь включает уже настроенный WireGuard. Рабочие подсети и их DNS остаются за ним, остальной трафик обрабатывается по правилам клиента. При отключении WireGuard во время управляемой сессии приватные назначения не пересылаются публичному прокси. Изменение VPN во время работы обрабатывается так же, как его наличие до запуска. Полная остановка клиента удаляет его правила; постоянная защита после этого в предложенный режим v1 не входит.

### Обновление

Обновление подписки и ru-direct сначала проходит загрузку и валидацию. Пустой/ошибочный ответ не стирает рабочие серверы и правила. Смена активного сервера после удаления его из подписки требует понятного уведомления; без утверждённой политики автоматического выбора сохраняется действующее соединение до следующего подключения.

## 5. Переносимость функций

| Функция | Linux v1 | Будущий Android |
| --- | --- | --- |
| Импорт, профили, правила, RU/EN | Полный объём | Общая логика и данные |
| Правила по приложениям/процессам | Desktop-каталог и проверенные executable/process-селекторы | Package identity и платформенная атрибуция; Linux PID/пути не переносимы |
| Простой/расширенный редактор | Одна модель политики, два представления | Та же модель с доступными мобильными селекторами |
| Выбор Xray/sing-box | Процессы | Нативные библиотеки в изолированных исполнителях |
| TUN и Fake DNS | Адаптер Linux | VpnService и платформенные callbacks |
| Проверки серверов | По запросу/политике | Те же семантика и результаты, более строгий бюджет фона |
| LAN и внутренний DNS | Исключения захвата и split DNS | Маршруты VpnService и маршрутизация DNS внутри приложения |
| Соседство с отдельным VPN | Приватные сети существующего VPN | Не поддерживается двумя VpnService в одном профиле |
| Доступ к WG-сетям | Внешний WG | Предлагается встроенный WG-профиль выбранного ядра |
| Трей/автозапуск | Desktop-интеграция | Уведомление, действие подключения, системный always-on |

Ограничение Android подтверждено [документацией платформы](https://developer.android.com/develop/connectivity/vpn). Встроенный WireGuard покрывает обычный профиль WireGuard; управляемые mesh-VPN и другие протоколы не становятся совместимыми автоматически.

## 6. За пределами первой реализации

Android-приложение, мобильный UI, собственная реализация транспортов/криптографии, собственный TUN-to-proxy движок, облачная синхронизация, плагины, скрипты подписок, запуск пользовательских команд, каскад из двух основных ядер и одновременное управление двумя основными TUN.

Проектирование Android-контрактов и проверка переносимости библиотеки входят в подготовку Linux-реализации. Сам Android-релиз — отдельный этап.
