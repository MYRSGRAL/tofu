# Исполнитель собственных nftables-таблиц

Продолжение P12: реальные эффекты сопровождаются durable intent и независимой
сверкой ОС. Это основание для защитных правил, а не завершённый kill switch:
пустая таблица сама по себе трафик не блокирует. Системный service/IPC, правила
маршрутизации, TUN и полная приёмка защиты остаются в общем плане.

## Границы доверия

- Вход — типизированные Ownership, Scope и Resource::NftTable; клиент не задаёт
  исполняемый путь, argv, shell-команду или сырой nft JSON.
- Системный `/usr/bin/nft` открывается с проверкой root-owned компонентов пути
  и файла. Исполнение использует закреплённый FD, а не повторный поиск по PATH.
- Network namespace закрепляется открытым FD; каждая операция проверяет его
  идентичность. Совпадение имени таблицы не доказывает владение.
- Метка содержит владельца, session/generation, namespace, record ID и scope.
  Идентичность требует точного совпадения family, имени и метки.
- stdout/stderr, длительность команды и вход ограничиваются. Неопределённый
  исход не превращается в успех и не удаляет запись журнала.

## Жизненный цикл

Создание начинается с durable intent. Повтор требует наблюдения ОС; чужая
таблица сохраняется. После эффекта состояние наблюдается повторно и только
подтверждённый результат записывается через reconcile.
Повтор ensure для записи CleanupRemaining отвергается до сетевого эффекта:
это replay прежнего intent, а не разрешение возродить ресурс после Stop.
Новый Apply должен использовать новое намерение и соответствующее поколение.

Удаление требует свежей сверки владения. `Journal::mark_cleanup` сохраняет
CleanupRemaining и сбрасывает разрешение на повторную попытку до внешнего
асинхронного эффекта. После отмены или crash нужна новая сверка, а не повтор
старого delete. PublicBlock имеет отдельный scope; его снятие в будущем
системном сервисе требует отдельной авторизации Unlock.

## Почему удаление использует handle

В nftables 1.1.7 JSON delete с полями family и ненулевым handle, без name,
кодируется как NFTA_TABLE_HANDLE в NFT_MSG_DELTABLE. Если передать также name,
parser выбирает имя; поэтому такой запрос запрещён конструкцией исполнителя.
Нулевой handle не является допустимым идентификатором удаления.
Первоисточник: [архив nftables 1.1.7](https://netfilter.org/projects/nftables/files/nftables-1.1.7.tar.xz),
`src/parser_json.c` (2965–2993); `src/mnl.c`, `mnl_nft_table_del`.

Ядро ищет таблицу по handle и family внутри нужного netns; имя при этом не
используется. Новая таблица получает следующее значение per-netns счётчика u64.
Таким образом, обычная замена таблицы тем же именем не превращает старый handle
в разрешение удалить новую таблицу.
[Исходники Linux 6.12](https://raw.githubusercontent.com/torvalds/linux/v6.12/net/netfilter/nf_tables_api.c):
`nft_table_lookup_byhandle`, `nf_tables_newtable`, `nf_tables_deltable`.

Handle не сохраняется как доказательство владения после перезапуска. После
уничтожения namespace, перезагрузки netfilter или переполнения u64 прежняя
идентичность не гарантируется. Закрепление namespace не защищает от действий
злонамеренного CAP_NET_ADMIN/root: он может скопировать метку или изменить
правила. Это не граница безопасности против администратора ядра.
