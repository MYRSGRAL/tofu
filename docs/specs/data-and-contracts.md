# yonik — данные, импорт и контракты

Проект [yonik](README.md) развивается с открытым исходным кодом (open source). Linux — первая платформа, Android — следующий этап.

## 1. Основные сущности

Имена ниже — названия контрактов, а не уже созданные типы или API.

| Сущность | Основные данные |
| --- | --- |
| Subscription | ID, имя, ссылка на секретный URL, формат, состояние обновления, последний snapshot |
| ServerProfile | ID, источник, отображаемое имя, адрес, протокол, транспорт, TLS, ссылки на секреты, ограничения ядра |
| NativeProfile | Исходный JSON, engine-id и версия схемы, отчёт разбора, ограничения управляемых настроек |
| RoutingPolicy | Упорядоченные личные правила, включённые пресеты, default action |
| RoutingRule | Стабильный ID, включение, группы условий источника/назначения, протокол/порт, действие, порядок и происхождение |
| ApplicationRef | Платформа, ID desktop entry или Android package, имя для UI и подтверждённое сопоставление селекторов |
| SourceSelector | Тип и значение: точный executable path, process name либо поддержанная платформенная идентичность; необходимые capabilities |
| ProcessCandidate | Снимок запущенной программы: PID/идентичность экземпляра, имя, доступный executable и область охвата предлагаемого правила |
| RoutingEditorState | Простой/расширенный режим, черновик и выделение; не меняет семантику RoutingPolicy |
| RouteExplanation | Входные данные, победившее правило, неизвестные признаки, поколение и тип доказательства: расчёт либо наблюдённый поток |
| PrivateNetwork | CIDR, DNS-суффиксы, resolver, способ доступа, поведение при потере VPN |
| DnsPolicy | Fake DNS, реальные upstream, bootstrap, исключения, IPv6 |
| ConnectionProfile | ServerProfile/NativeProfile, выбранное ядро, RoutingPolicy, DnsPolicy, режим TUN/локального прокси |
| ProbeResult | Сервер, ядро, метод, URL, network-generation, длительность, этап ошибки, время проверки |
| EngineDescriptor | Версия, источник, хэш артефакта, поддерживаемые возможности и версия адаптера |
| AppliedSession | ID сессии, поколения плана/сети, ядро, принадлежащие ресурсы, состояние |

Адреса и правила валидируются до сохранения: порты 1–65535, канонические CIDR, нормализованные домены, допустимые размеры строк и коллекций. Display name не является идентификатором сервера. Смена имени в подписке не должна терять избранное; смена адреса/ключевых параметров означает новый fingerprint.

Простой редактор изменяет те же записи RoutingRule, что и расширенный. Группы условий соединяются через И, значения внутри группы — через ИЛИ; произвольного вложенного языка выражений на старте нет. Desktop display name и PID не являются устойчивыми селекторами приложения. Пути Linux хранятся как явно платформенные данные и проверяются host, без файловых операций внутри domain. Сопоставление ApplicationRef → SourceSelector версионируется; неприменимые правила сохраняются, но требуют разрешения перед активацией. Детали и примеры — в [контракте редактора](routing-and-tray.md).

## 2. Импорт

Поддерживаемые входы: URL подписки, отдельная URI-ссылка, строки URI, Base64-обёртка над поддерживаемым текстом, JSON Xray/sing-box, ручная форма. Base64 — кодирование, а не самостоятельная схема конфигурации.

Порядок: ограниченное чтение → распознавание → максимум один слой Base64 → разбор → нормализация → проверка возможностей → отчёт → транзакционное сохранение. Рекурсивное угадывание кодировок не используется. JSON не исполняет скрипты и не загружает дополнительные файлы во время разбора.

Предлагаемые первоначальные пределы: до 8 MiB переданного тела и до 32 MiB после распаковки/декодирования, 20 000 записей, глубина JSON до 64. Это защитные лимиты, которые можно изменить после стресс-тестов. Ограничения применяются потоково и до крупных аллокаций. Отчёт содержит индекс/поле ошибки; ключи и URL-токены скрыты.

Политика частично ошибочного импорта: пользователь видит число принятых и отклонённых записей и подтверждает сохранение валидной части. Обновление существующей подписки с массовыми ошибками/пустым результатом не заменяет рабочий snapshot автоматически.

### Протоколы

Предлагаемый первичный набор нормализованных профилей: VLESS, VMess, Trojan, Shadowsocks, HTTP CONNECT и SOCKS5; Hysteria2/TUIC — при наличии capability соответствующего адаптера. Варианты транспорта, REALITY и дополнительные расширения учитываются отдельно. Точный обязательный набор расширений должен быть согласован перед реализацией импортера.

Текстовая схема `vless://` сама по себе не доказывает поддержку всех query-параметров обоими ядрами. Неизвестный параметр сохраняется в исходнике и отражается в отчёте, а критичный неподдерживаемый параметр блокирует активацию.

### Полный JSON

Управляемый профиль извлекает известные серверные параметры, а TUN/DNS/маршруты генерирует приложение. Engine-specific NativeProfile сохраняет исходную конфигурацию без ложного обещания преобразовать её в другое ядро.

Для активации полного JSON адаптер выдаёт план согласования принадлежащих приложению полей: listener, TUN, DNS, пути файлов, API и routing. Конфликт либо явно разрешается при импорте в управляемый профиль, либо режим сообщает, какие общие настройки недоступны. Неизвестные поля не удаляются тихо. Непроверенный произвольный JSON не передаётся привилегированному процессу.

Для v1 предпочтителен управляемый импорт. Оpaque хранение исходника обеспечивает сохранность, но не является обещанием запускать любой возможный native-конфиг.

## 3. Обновление подписок и наборов

Источник загружается с TLS-проверкой, лимитом редиректов и размера. HTTPS — обычный режим; HTTP может быть разрешён явно для локального/доверенного источника. При смене origin секретные заголовки не переносятся. URL, содержащие credentials, не отображаются целиком.

Публичные подписки по умолчанию не могут через редирект обратиться к loopback, link-local или приватному адресу. Для локальной подписки создаётся явное исключение источника. Проверяются и DNS-результат, и фактический peer подключения; отказ не вызывает автоматического обхода политики.

Используются ETag/Last-Modified, если их предоставляет источник. Выбор прямого или проксируемого пути загрузки задаётся политикой и не меняется скрыто после ошибки. Последняя рабочая конфигурация доступна офлайн.

Смена snapshot атомарна для метаданных. Активная сессия получает новое поколение только после проверки; обновление списка само по себе не требует разрыва текущего соединения. Таймеры, частота и работа от батареи описаны в [производительности](performance.md).

## 4. Контракты платформенных портов

| Порт | Действия | Гарантия |
| --- | --- | --- |
| EngineHost | Возможности, проверка плана, старт, остановка, статистика, проверка outbound | Версионный контракт; никакого shell command от UI |
| NetworkHost | Снимок, наблюдение, подготовка, применение, откат/освобождение | Владение только своими ресурсами; повторное освобождение безопасно |
| ResolverHost | Снимок DNS, split DNS, адресный сброс кэша | Чужие зоны/линки сохраняются |
| CredentialStore | Получить/сохранить/удалить секрет по opaque ID | UI и логи получают маскированное представление |
| Repository | Транзакции и миграции | Один writer, согласованные snapshots |
| FetchHost | Ограниченная загрузка по заданному сетевому пути | Отмена, timeout и учёт выбранной сети |
| Clock/Scheduler | Время, дедлайны, разрешённое окно фоновой работы | Подставные часы для тестов; без таймера на каждый сервер |
| PowerHost | Батарея, metered, состояние UI, фоновые ограничения | Событийное обновление политики задач |
| ApplicationCatalog | Страницы desktop/package-каталога, ограниченный снимок процессов, проверка сопоставления приложения | Нет запуска Exec, передачи argv/environment или постоянного фонового обхода процессов |
| DesktopShellHost | Трей, уведомления, восстановление регистрации и открытие нужного экрана | Только команды controller и подписки на состояние; не владеет сетевой сессией |

ExecutionPlan содержит структурированные настройки, resource IDs, версии и ссылки на secrets. Конкретные пути Linux, дескрипторы Android и IPC-объекты создаёт host. Внешний интерфейс не принимает указатели или числовой FD как переносимое значение.

PreparedPlan привязывается к network-generation, версии сопоставлений приложений и хэшу проверенной конфигурации. Между Validate и Apply окружение проверяется повторно. Потеря прав, смена default route, уход VPN или изменение необходимого executable/package mapping делают план устаревшим и запускают пересчёт.

## 5. События, отмена и ошибки

Команды имеют request-id и идемпотентность в рамках сессии. Повтор Stop не создаёт ошибку отсутствующего ресурса. Connect с тем же request-id возвращает результат той же операции. UpdateProfile не означает ApplyProfile.

Событие содержит event-id, session-id, generation, тип и ограниченную полезную нагрузку. Состояния доставляются надёжно либо восстанавливаются запросом snapshot. Статистика может объединяться до последнего значения; логи — отбрасываться по лимиту с явным счётчиком потерь. Старые callbacks после отмены не оживляют сессию.

Ошибка включает стабильный код, message-key, безопасные параметры, этап, повторяемость и диагностическую причину. Минимальные категории: невалидный импорт, неподдерживаемая возможность, потеря разрешения, конфликт маршрутов, DNS, запуск ядра, timeout, TLS, endpoint, устаревший план, ошибка очистки. `DNS_POLICY_AMBIGUOUS` обозначает неоднозначный защищённый набор адресов, `DNS_POLICY_UNRESOLVED` — неудачу обязательного разрешения для выбора маршрута; их семантика определена в [сетевом контракте](networking.md).

RU/EN-представления живут в каталогах переводов. Исходные сообщения стороннего ядра доступны как технические детали и не выдаются за полностью переведённый продуктовый интерфейс. Никакой логики по сравнению с локализованной строкой.

## 6. Хранение

SQLite хранит метаданные, версии схем и ссылки на защищённые значения. Записи с секретами, исходные подписки и raw JSON шифруются отдельно ключом хранилища. Для Linux предлагается Secret Service; для Android — Android Keystore. Доступ к ключу после перезагрузки/блокировки устройства является частью политики автоподключения и требует платформенной проверки.

При недоступности хранилища допустим явный сеансовый режим без постоянного сохранения credentials. Автоподключение тогда недоступно. Секреты не превращаются в открытый JSON как скрытый fallback.

Файлы состояния создаются только в каталоге приложения с ограниченными правами. Сгенерированный рабочий конфиг передаётся через поддерживаемый безопасный канал или краткоживущий файл с ограниченными правами. Точное имя файла/ключи не попадают в командную строку, журналы или диагностический экспорт.

Миграция схемы транзакционна, с резервной копией до разрушительных изменений. Старое приложение не открывает новую схему на запись. Откат ядра и откат схемы приложения — разные операции; обновление одного не требует второго автоматически.

## 7. Версии и capabilities

Начальные кандидаты, проверенные по релизам 08.11.2026: Xray-core 26.10.31 и sing-box 1.14.4. Совместимость приложения с ними ещё не измерялась. Компилятор поддерживает явный диапазон версий/схем; неизвестная версия не получает статус совместимой по одному имени бинарника.

Capability учитывает engine-version, platform, build-features и adapter-version. В неё входят протоколы/транспорты, TUN, Fake DNS, диагностика, типы правил, private-WG и конкретные process/application-селекторы с ограничениями TCP/UDP и прав. Поддержка process name не доказывает поддержку PID, cgroup, desktop ID или Android package. Неподдерживаемое условие не удаляется из конфига тихо. Не все возможности sing-box из документации ветки разработки доступны в стабильном артефакте.

Desktop-ядра поставляются закреплёнными пакетами/артефактами. Обновление валидирует целостность, запускает smoke-проверку и сохраняет одну предыдущую рабочую версию. Автоматическая бесконтрольная замена работающего ядра по `latest` не планируется. На Android нативные ядра обновляются вместе с APK.

## 8. FFI

Предлагается UniFFI для вызова общей Rust-логики из Kotlin. События передаются порциями; большой список серверов — страницами. [UniFFI поддерживает Kotlin и async-интерфейсы](https://mozilla.github.io/uniffi-rs/latest/), но thread affinity и освобождение callbacks необходимо проверить прототипом.

FFI-контракт версионируется независимо от storage schema. Нет передачи panic через ABI. Явные закрытие, отмена и ownership handles обязательны; сборщик мусора Kotlin не определяет момент остановки VPN. Граница FFI не участвует в обработке каждого сетевого пакета.

Additive policy-bearing Prepare/RPCv1 описан в `helper-service.md`, раздел
`system_profile_policy`. Engine `policy_wire::SystemPolicy` владеет проверенной
immutable domain Policy и закрытым плоским wire DTO. Linux не принимает UI bool
вместо requirements, native JSON либо произвольный путь executable ядра.
