# yonik — проверки и порядок реализации

Проект [yonik](README.md) развивается с открытым исходным кодом (open source). Linux — первая платформа, Android — следующий этап.

Этот документ задаёт план приёмки. Начальная реализация и часть изолированных проверок уже выполнены; результаты и ограничения находятся в [evidence](../validation/). Наличие сценария в таблицах ниже не означает, что он пройден. Полные gates пока не закрыты.

## 1. Ранние проверки архитектуры

| Gate | Что выяснить | Доказательство готовности |
| --- | --- | --- |
| G-LINUX | Нативный TUN обоих ядер, минимальные права, владение сетью | Отдельный воспроизводимый запуск каждого ядра; TCP/UDP, DNS, stop/crash cleanup; перечень нужных capability |
| G-DNS | Fake DNS, общий порядок домен/CIDR, ru-direct, split DNS приватного VPN | Трасса запросов и маршрутов для обоих ядер; совпадение решений D-01…D-07 ниже; ни fake-IP, ни внутренняя зона не попадают в публичный путь |
| G-APP | Атрибуция приложений/процессов в Linux TUN двух ядер | A-01…A-08, реальные TCP/UDP/IPv4/IPv6-маршруты и права, одинаковое общее подмножество правил; стоимость определения владельца измерена |
| G-ANDROID | FFI, native-исполнители, TUN FD, protect и атрибуция приложений | Маленький технический host без продуктового UI: каждый engine передаёт TCP/UDP, останавливается, переживает revoke; package callbacks проверены отдельно от исключения приложения из TUN |
| G-UI | Выбранный toolkit на KDE Wayland | Кириллица/EN, ввод, clipboard, дробный масштаб, keyboard, T-01…T-04, два режима редактора и отсутствие постоянных redraw в фоне |
| G-POWER | Стоимость controller, tray-host, платформы и process attribution | Отчёт по baseline и P-01…P-08 из performance.md; оптимизация не меняет правильность маршрута |

Неудачный gate меняет соответствующий адаптер/решение до расширения реализации. Например, отсутствие пригодного TUN-FD API в desktop CLI не отменяет общую модель, но определяет service/capability-вариант запуска.

Android gate нужен до того, как Linux-only детали станут публичным API общей библиотеки. Он не означает разработку полного Android-клиента сейчас. Выполнение любых прототипов требует отдельного перехода пользователя от документации к реализации.

## 2. Тесты общей библиотеки

- Табличные тесты URI/JSON/Base64 на валидных, повреждённых, больших и неоднозначных данных.
- Property/fuzz-тесты декодирования, вложенности, IDNA, IPv4/IPv6, префиксов, размеров и неизвестных параметров.
- Дедупликация и обновление подписки: переименование, удаление, смена credentials, пустой ответ, частичный импорт.
- Детерминированные состояния: отмена Connect, два Connect, Stop во время Validate/Apply, позднее событие старого поколения, повтор Stop, потеря host.
- Порядок правил и их перенос в оба engine-конфига: ручное правило выше ru-direct, исключения приватной сети, конфликт суффикса и CIDR.
- Ошибки и переводы: все собственные message-key присутствуют в RU/EN; параметры не раскрывают credentials.
- Миграции/backup: прерывание транзакции, старая версия схемы, повреждённый snapshot, закрытое хранилище секретов.
- Scheduler с подставными часами: backoff, отмена, metered/battery saver, скрытый UI, отсутствие неограниченных очередей.
- Редактор правил: И между группами/ИЛИ внутри группы, порядок, составные правила в простом режиме, переход между режимами без потери данных, явное отклонение неподдерживаемого селектора.
- Каталог приложений: дубликаты имён, смена executable mapping, переиспользование PID, отмена/пагинация, отсутствие argv/environment в модели и диагностике.

Проверка структуры JSON дополняется запуском валидатора закреплённого ядра. Golden-файл без реального парсинга ядром не доказывает совместимость. В fixtures используются только искусственные адреса/секреты.

### Обязательные случаи G-DNS

Ожидания следуют [общему сетевому контракту](networking.md), а не текущему поведению одного из движков. Матрица включает оба ядра, Fake DNS on/off и разрешённые семейства IPv4/IPv6. Для каждого случая фиксируется вид входа: имя, fake-IP с известным mapping или уже выбранный реальный IP. Эквивалентность ядер проверяется при одинаковом входе; полный набор адресов домена не подмешивается к буквальному IP. Порядок адресов в ответах переставляется; важны итоговый путь и отсутствие запрещённых DNS/сетевых запросов, а не только содержимое конфигурации.

| ID | Входные условия | Ожидание |
| --- | --- | --- |
| D-01 | Личное доменное правило «прокси», ответ входит в старший приватный CIDR | Приватный VPN либо блокировка при его отсутствии; ранний fake-IP не закрепляет публичный proxy |
| D-02 | Личное доменное правило «прокси», совпадающий младший ru-direct CIDR | Личное правило выигрывает; реальное разрешение нужно только для ещё не решённых старших условий |
| D-03 | Доменное назначение разрешается в несколько публичных A/AAAA, подходящих под разные CIDR-правила | Побеждает первое правило, которому соответствует хотя бы один адрес; порядок A/AAAA не влияет на действие. Контрольный вход с уже выбранным реальным IP проверяет только этот IP |
| D-04 | Ответ смешивает приватный и публичный адрес либо два приватных VPN | `DNS_POLICY_AMBIGUOUS`, соединение не отправлено ни по одному случайному пути |
| D-05 | Необходимый lookup завершился timeout/SERVFAIL либо неполный ответ не исключает старшее условие | `DNS_POLICY_UNRESOLVED`, нет fallback к DIRECT, младшему правилу или системному DNS; отдельный контроль NODATA одного семейства |
| D-06 | Внутренняя зона, VPN отключён; публичный resolver мог бы ответить | Имя не отправляется публичному resolver, соединение блокируется; после возврата VPN работает его DNS |
| D-07 | Ответ/сеть изменились после TTL, сменился engine-generation либо приложение использует старый fake-IP | Старое решение не переиспользуется как актуальное; повторная классификация не обходит приватную защиту; неизвестный mapping даёт отказ |

Дополнительно проверяются буквальный IP со sniffed-именем, DNS-путь самого policy-resolver и bootstrap без рекурсии. Отдельный fixture меняет адрес между классификацией и подключением: исполнитель не должен обойти приватную проверку вторым локальным lookup. Передача имени удалённому прокси учитывается как отдельный режим с пределом контроля его DNS.

## 3. Linux: обязательная интеграционная матрица

Все основные сценарии повторяются для Xray и sing-box; Fake DNS on/off — отдельная ось.

| Сценарий | Ожидаемый результат |
| --- | --- |
| TUN без внешнего VPN | TCP/UDP идут по правилам, собственный transport не зацикливается |
| WireGuard запущен до клиента | Приватные CIDR и внутренний DNS доступны через WG |
| WireGuard включён после клиента | Исключения обновлены по событию, без полного restart всех подписок |
| WireGuard выключен при активном клиенте | Сохранённые приватные назначения блокируются, не уходят в публичный proxy |
| WireGuard включён повторно | Его маршруты/внутренний DNS восстанавливаются |
| Остановка нашего клиента | Удалены только собственные ресурсы; работающий WG и LAN сохранены |
| Сбой ядра и восстановление при отсутствующем WG | Приватные CIDR и DNS-зоны защищены между попытками; helper сохраняет владение защитой |
| Повторы исчерпаны / явное отключение при сохранённом пресете | Оба пути проходят полную очистку; после неё нет собственных постоянных правил, статус отражает причину остановки |
| Ошибка удаления маршрута/правила/DNS или недоступный helper | Статус «Ошибка очистки», остатки перечислены; успешное отключение и полная защита не заявляются |
| Смена Wi-Fi/Ethernet | Пересчитан physical egress, результаты старого ping помечены устаревшими |
| Сон/пробуждение | Нет старого TUN/процесса-дубликата, восстановление ограничено политикой |
| Сбой ядра/controller/helper | Проверяемая остановка/восстановление, понятный статус, без бесконечного restart |
| Fake-IP перед сменой ядра | Старый mapping не трактуется новым движком как действительный |
| ru-direct обновился с ошибкой | Работает предыдущий snapshot, личные правила сохранены |
| Смешанный IPv4/IPv6 | Нет неоговорённого обхода TUN по IPv6 |
| Низкий MTU, большие TCP/UDP | Нет скрытого зависания больших пакетов |
| LAN и обнаружение | Роутер/NAS/SSH и mDNS работают в пределах заявленного пресета |
| Личный домен конфликтует с ru-direct | Побеждает личное правило, виден источник решения |
| Неизвестный native JSON | Активация остановлена с конкретным полем, исходник сохранён |
| Два входа в приложение | Один controller и одна основная сессия |

Тесты сетевых отказов сначала выполняются в изолированном стенде/namespace с локальными серверами. Применение к реальной сети пользователя — отдельный согласованный этап. Docker build/up не требуются для самого комплекта документов и не предполагаются без просьбы.

### Обязательные случаи трея

| ID | Сценарий | Ожидание |
| --- | --- | --- |
| T-01 | Закрыть окно при активной сессии, открыть из трея и повторным запуском | Подключение живёт, controller один; возвращается актуальное состояние без повторного Connect |
| T-02 | Подключить, выбрать другой сервер, отключить, затем «Выйти и отключиться» через меню | Те же команды и ошибки, что в окне; подтверждённая очистка перед нормальным выходом; ошибка очистки не исчезает вместе с меню |
| T-03 | Перезапуск Plasma/службы трея и запуск без работающего трея | Значок восстанавливается без перезапуска VPN; без трея сохраняется доступное окно управления |
| T-04 | Трей в простое, состояния восстановления/ошибки, RU/EN, масштаб Wayland | Статусы читаемы, секретов нет; нет фоновой анимации/опроса скорости, память и CPU включены в P-01…P-03 |

### Обязательные случаи G-APP и редактора

| ID | Сценарий | Ожидание |
| --- | --- | --- |
| A-01 | Две обычные программы одновременно: proxy, DIRECT и block по проверенным executable | Каждый новый поток получает ожидаемый путь; одинаковый результат на обоих ядрах; второе основное ядро не запускается |
| A-02 | Браузер/программа с дочерним сетевым процессом; отдельные fixtures AppImage/Flatpak/Wine | Идентифицирован фактический владелец; baseline обычных приложений работает, неизвестный охват упаковки показан без ложного обещания наследования |
| A-03 | TCP и UDP, IPv4/IPv6, короткие соединения, системный DNS и локальный proxy inbound | Нет ложного сопоставления соседнему приложению; resolver не выдаётся за программу-инициатор DNS; неподдерживаемый режим отмечен явно |
| A-04 | Приложение + домен/CIDR + порт, конфликт с ru-direct и приватной сетью | И/ИЛИ и порядок совпадают с моделью; старшие приватные исключения сохраняются; ложный источник не запускает ненужный lookup для этого правила |
| A-05 | Неизвестный владелец отдельного потока, затем полная потеря возможности attribution | Для потока показано применение обычных правил/default; отсутствие механизма целиком блокирует активацию новой политики с process-правилами |
| A-06 | Одинаковые имена разных executable, новый PID после перезапуска, PID занят другой программой | Точный путь не смешивается с basename; PID из выбора не становится вечным правилом; смена сопоставления инвалидирует PreparedPlan |
| A-07 | Простой → расширенный → простой; составное правило, изменение порядка, ошибка Apply | Семантика и ID сохраняются; скрытые сложные правила видны и действуют; неудача Apply оставляет прежнее поколение; старые потоки не выдаются за мигрировавшие |
| A-08 | Неизвестный платформенный селектор, ограниченный каталог, открытие/закрытие выбора процессов | Нет тихого удаления условий или запуска Exec; чужие аргументы/секреты не читаются; скрытый экран не сканирует процессы; отказ объясним |

G-APP не считается пройденным только потому, что ошибки отображаются красиво: базовые правила обычных Linux-приложений и executable должны реально работать с обоими ядрами. Неудача baseline возвращает архитектуру на пересмотр. Нестандартные упаковки и дополнительные PID/cgroup-селекторы имеют отдельную явно заявленную матрицу по O-10.

## 4. Проверки задержки

- TCP до работающего адреса при неверных credentials показывает достижимость TCP, но HTTPS-through-proxy — ошибку туннеля.
- UDP-only профиль получает «TCP неприменим», при этом HTTPS-through-proxy может работать.
- Тестовый домен, попавший в ru-direct, всё равно проверяется через выбранный outbound.
- Сервер A не измеряется через текущий сервер B или переменные системного proxy.
- DNS failure, timeout, TLS failure, HTTP redirect/ошибка и отказ proxy различимы.
- Три выборки одного endpoint дают медиану; другой endpoint и другая сеть имеют отдельную идентичность результата.
- Пакет из 10 000 проверок ограничивает параллелизм, допускает отмену и не оставляет probe-runtime.
- Проверка недоступности gstatic не выдаётся за доказательство полной недоступности интернета.

Контрольный endpoint в CI — локальный управляемый HTTPS-сервис с тестовым доверенным CA, без отключения TLS validation. Публичный URL проверяется отдельным smoke-сценарием, чтобы чужая сеть не делала unit/integration-набор недетерминированным.

## 5. Будущий Android

Проверить VPN permission grant/revoke, Activity уничтожена, service перезапущен, UI подключился повторно, Wi-Fi → мобильная сеть → Wi-Fi, offline, battery saver, Doze, always-on и системную блокировку обхода VPN.

Для каждого ядра: TUN FD ownership, TCP/UDP protect, DNS bootstrap, отсутствие второго Go runtime, завершение неактивного worker, Binder death, timeout callback и ограничения очереди. Отдельно — встроенный WG к приватным подсетям вместе с публичным proxy, включая исчезновение WG-peer.

Для правил приложений: package/UID attribution в каждом worker, два приложения с разными действиями, общий процесс/UID и неизвестный владелец, смена/удаление пакета, неприменимые Linux-селекторы при импорте. Проверяется разница между DIRECT внутри ядра и исключением из VpnService, влияние на приватные сети, пересоздание TUN после изменения allow/disallow list и системная блокировка обхода VPN. Один успешный allowlist не доказывает поддержку составных «приложение + назначение» правил.

Все эти проверки относятся к обычному Android без root. Work profile, root, OEM-специфика и произвольное внешнее VPN-приложение не считаются универсальным решением несовместимости двух VpnService.

## 6. Проверки границ доступа

Недоверенный пользователь не запускает через helper произвольный бинарник, не читает чужой профиль, не подменяет plan после Validate и не удаляет чужой маршрут. Проверяются symlink/path traversal, oversized IPC, отозванная авторизация, рабочий каталог, секреты в argv/log/export и неподдерживаемый raw JSON.

Android-компоненты engine worker не экспортируются; только наш service передаёт дескрипторы и команды. Ошибка callback не превращается в «успех» и не включает обход protect.

## 7. Этапы реализации

### Этап 0 — текущая документация

Результат: требования, контракты, сетевые инварианты, риски Android, измеримые бюджеты и открытые решения. Визуальное оформление и конкретный toolkit ещё не утверждены.

### Этап 1 — проверка самых рискованных связей

G-LINUX, G-DNS, G-APP, минимальная сборка общей библиотеки под Android и G-ANDROID. На выходе закреплены версии ядер/обёрток, права, границы распознавания приложений и lifecycle. Если Android host потребует изменения контрактов, это происходит здесь.

### Этап 2 — общая логика

Импорт, хранение, capabilities, единая модель источников/назначений и двух редакторов, компиляторы конфигов, состояния, scheduler, переводы ошибок. Приёмка — unit/property-тесты и реальный config-check обеих версий.

### Этап 3 — Linux-сеть

Helper, TUN, DNS/Fake DNS, атрибуция процессов, приватные VPN, ru-direct, обновление сети и cleanup. Приёмка — Linux-матрица и G-APP без готового продуктового UI, через минимальный диагностический host.

### Этап 4 — Linux-приложение

Отдельное согласование UI, G-UI, основные экраны, обязательный трей, простой/расширенный редактор, выбор приложений, проверки серверов и диагностика. G-POWER с P-01…P-08 повторяется на собранном продукте.

### Этап 5 — поставка Linux

Arch-пакет yonik, trusted helper/ядра, обновления и откат, документация пользователя RU/EN, проверка лицензий. Для открытой поставки готовы выбранная лицензия, собственные исходники, тесты, сборочные инструкции и необходимые notices зависимостей. Перед выпуском все обязательные FR имеют evidence, а остаточные ограничения перечислены явно.

### Этап 6 — отдельный Android-клиент

Нативный UI и VpnService-host поверх проверенных контрактов, встроенные приватные WG-профили, Android-матрица и измерения на физическом телефоне. Публичный Android-релиз не входит в Linux v1.

## 8. Что сохраняется как evidence

Версии/хэши ядра и адаптера, ОС/устройство, обезличенный fixture, применённый план, состояние до/после, результаты маршрутов/DNS, метрики и сценарий воспроизведения. Секретные конфиги и подписки в evidence не попадают.

Для Rust будущие проверки: fmt, clippy по всем применимым targets без warnings, релевантные тесты и Android compile-check общей библиотеки. Build-каталоги располагаются в transient-каталоге с удерживаемым lock по правилам пользователя; результаты переносятся в workspace перед очисткой. Сейчас build-каталог не создаётся.

## 9. Покрытие требований документами и приёмкой

## 10. Дизайн-review документации

Независимый read-only review предыдущей версии комплекта из 10 документов выполнен 8 ноября 2026 года. Он не обнаружил фундаментального противоречия в разделении компонентов или предлагаемой Android-схеме, но выделил два уточнения:

- P1: срок действия защиты приватных назначений расходился между сетевым документом и cleanup-контрактом. Добавлена таблица состояний, синхронизированы lifecycle, Linux-адаптер, ADR-006 и приёмка остановки.
- P2: отсутствовал общий порядок DNS/Fake-IP и CIDR при нескольких адресах и ошибке разрешения. Добавлена таблица решений, определены два кода отказа и случаи D-01…D-07.

Уточнения внесены основным автором после review. Последующее дополнение обязательным треем, правилами приложений и двумя режимами редактора расширило комплект до 11 документов. Оно не входило в тот независимый проход; повторный независимый review не выполнялся. Проверка документации не доказывает совместимость конкретных wrappers, конфигов и сетевых механизмов: для этого остаются обязательными G-LINUX, G-DNS, G-APP и G-ANDROID. Бюджеты ресурсов остаются целями для измерения.
